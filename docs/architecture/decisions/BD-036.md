# BD-036 — Multiple BOM variants are allowed; receiving selects the BOM, and contractor pricing has an explicit pricing unit

**Status:** CONFIRMED

## Decision

CY Web allows more than one BOM / material recipe for the same finished Item. A finished Item is not constrained to one current BOM merely because Legacy lookup code historically used the first matching `finId`.

When a received finished Item has multiple applicable BOMs, the receiving workflow must require the user to select which BOM was actually used for that received quantity. CY Web must not silently choose the first matching BOM or guess from list order.

If exactly one applicable BOM exists, the UI may use that BOM directly without forcing an unnecessary choice.

## Receiving and stock-consumption rule

The selected BOM is part of the receiving business fact.

For each receiving line / received finished Item, CY Web must preserve enough information to identify the BOM used for that receipt. The resulting component-consumption stock movements are derived from that selected BOM and the received quantity.

Historical receiving and stock movements must not be recalculated merely because the BOM is edited later. A later BOM revision affects future receipts only unless an explicit receiving correction workflow is performed.

This replaces the Legacy behavior in which consumption calculation effectively used `find(m => m.finId === item.id)` and therefore depended on whichever matching BOM happened to be returned first.

## BOM lifecycle implication

- Multiple BOM records may reference the same finished Item.
- Each BOM has its own stable internal identity.
- A BOM that has already been referenced by retained receiving/history data must not be hard-deleted in a way that breaks that history; the master-data retention rule from BD-030 applies.
- Exact naming/version fields for distinguishing BOM variants are deferred to the Data Dictionary/UI design, but the user must be able to tell the alternatives apart when selection is required.

## Contractor pricing rule

Each Contractor Price record is defined by:

```text
Contractor + Item + pricing unit + unit price
```

The pricing unit is explicit. It is not permanently assumed to be the Item base unit.

Examples:

```text
Item A001  $3 / 個
Item A001  $250 / 包
```

The pricing unit must be one of the valid units supported for that Item by the canonical Item/unit-conversion model.

## Pricing calculation

When the receiving unit differs from the Contractor Price pricing unit, CY Web converts the received quantity into the pricing unit using the Item unit-conversion rules before calculating the charge.

Conceptually:

```text
received quantity + received unit
        -> canonical unit conversion
        -> quantity in pricing unit
        -> quantity in pricing unit × unit price
        -> subtotal
```

The pricing snapshot must preserve the pricing unit, applied unit price, relevant quantity used for pricing, and resulting subtotal so later changes to Contractor Price or Item conversion settings do not silently rewrite historical priced orders.

If no valid conversion path exists between the received unit and the pricing unit, CY Web must not silently calculate with mismatched units; the data must be corrected before automatic pricing can complete.
