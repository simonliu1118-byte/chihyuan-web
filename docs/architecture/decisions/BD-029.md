# BD-029 — Sales work orders become voidable, not hard-deletable, after ERP issuance

**Status:** CONFIRMED

## Decision

CY Web sales work orders may be hard-deleted only while they remain a purely pre-ERP draft/business work order:

- status is `created / 已建檔`; and
- no SMART ERP sales-order number has been filled.

Once an ERP number has been filled and the work order has entered `issued / 已出單` or any later fulfillment state, ordinary hard delete is prohibited.

## Void semantics

After ERP issuance, the explicit business action is **作廢工單** rather than delete/cancel wording.

A work order may be voided directly from `issued / 已出單`, `waiting_stock / 等到貨`, `picked / 已撿貨`, or `shipped / 已出貨`. Customer cancellation or another business reason for terminating the order does **not** require the fulfillment status to be reversed step-by-step before voiding.

Voiding means the work order is terminated and will no longer continue through fulfillment. It preserves the CY Web work-order identity, ERP number, original line details, status/history that occurred before voiding, and the void event itself. The void event records actor and time through the existing workflow/audit semantics. Whether a void reason is mandatory is left to the later high-risk/correction UX policy.

A voided work order remains searchable and traceable; it must not disappear as if the ERP-linked business event never existed.

## Reversal is separate from voiding

Fulfillment reversal remains supported as a separate business function when the order is still valid but the operational state needs correction. For example, the existing `shipped / 已出貨 → picked / 已撿貨` reversal remains available under the appropriate permission/history rules.

The semantic distinction is:

- **reversal / 退回** — the work order remains active and fulfillment will continue after correcting its state;
- **void / 作廢** — the work order is terminated and no further fulfillment is expected.

A user must not be forced to perform a reversal merely to make the **作廢工單** action available.

If a future fulfillment operation creates a separate physical or accounting side effect that independently requires correction, that correction is handled by its own domain rule; it is not a prerequisite for changing the work order to voided solely for workflow semantics.

## Legacy change

Legacy Desktop currently allows an administrator to hard-delete some ERP-issued work orders before `已出貨`. CY Web intentionally tightens this behavior because ERP issuance creates an external formal-document relationship that must remain traceable.

Legacy's existing fulfillment reversal behavior is preserved where valid, but reversal and voiding are modeled as independent actions.
