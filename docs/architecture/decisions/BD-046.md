# BD-046 — Backup service contract, storage-provider boundary, and portable package format

**Status:** CONFIRMED

## Decision

CY Web backup architecture is split into two layers:

1. an application-level `BackupService`, which owns backup creation, verification, retention, restore orchestration, authorization, audit, and D1-specific safety rules; and
2. a storage-level `BackupStorageProvider`, which only stores and retrieves opaque backup objects.

The storage provider must not contain D1 restore semantics, Super Admin authorization, schema migration logic, or application-domain decisions. This keeps GCS replaceable by another object-storage backend without rewriting business restore behavior.

## Application-level contract

The exact TypeScript names may be finalized during implementation, but the service boundary must cover these semantics:

```text
BackupService
- createBackup()
- listBackups()
- verifyBackup(backupId)
- restoreBackup(backupId)
- applyRetention()
```

`restoreBackup` is intentionally owned by `BackupService`, not by the storage provider.

The service is responsible for:

- reading a consistent application backup payload from D1;
- building the portable package and manifest;
- computing application-level SHA-256 integrity data;
- writing the package through `BackupStorageProvider`;
- reading the stored object back and verifying it before recording success;
- listing only backup sets that belong to the current application/workspace scope;
- validating application ID, backup format version, schema compatibility, counts, and checksums before restore;
- enforcing Super Admin-only restore and the double-confirmation workflow from BD-044;
- recording structured audit evidence for backup/restore operations;
- applying retention policy without deleting a backup required by an in-progress restore or other protected operation.

## Storage-provider contract

The concrete GCS implementation sits behind an opaque object-storage boundary. The minimum conceptual operations are:

```text
BackupStorageProvider
- putObject(key, bytes, metadata)
- getObject(key)
- listObjects(prefix)
- deleteObject(key)
```

A provider may expose additional capabilities internally, but application code must not depend directly on GCS-specific bucket APIs, object naming quirks, signed URLs, or credential formats.

## Backup set layout

A logical backup is a backup **set**, not merely an arbitrary file. The portable layout is:

```text
<app-scope>/<backup-id>/
├─ manifest.json
└─ data.json
```

The exact GCS bucket name and top-level production prefix are deployment configuration and must not be hard-coded in Public Git.

`backup-id` is a stable unique identifier generated for one backup operation. It must not be inferred solely from a timestamp.

## `manifest.json`

The manifest is small, human-readable metadata used to determine whether a backup is safe to consider for restore. It contains at least:

```text
format
formatVersion
backupId
appId
appVersion
schemaVersion
createdAtUtc
sourceDatabaseEngine = d1
workspaceScope / tenant scope when applicable
tableCounts / recordCounts
dataObjectName
dataSha256
dataByteLength
backupStatus
```

Production D1 database IDs, Cloudflare account IDs, secrets, GCS credentials, and other environment-specific sensitive identifiers are not embedded as required portable fields.

`backupStatus` is written as a final valid state only after upload and read-back verification has succeeded. An incomplete object set must never be presented as a restorable backup.

## `data.json`

`data.json` contains the portable application data snapshot required to reconstruct the application database.

Requirements:

- UTF-8 JSON;
- deterministic schema defined by the application backup format version;
- tables/entities identified explicitly rather than relying on source row order;
- sufficient IDs and relationship data to rebuild referentially consistent records;
- no runtime secrets, password plaintext, OTPs, session tokens, refresh tokens, API tokens, or credential material;
- preserve authoritative decimal/text/date representations without binary-float reinterpretation;
- values needed only for deployment infrastructure are excluded.

The internal payload may evolve between `formatVersion`s. A restore implementation must reject an unsupported format rather than guessing.

## Integrity verification

Application-level integrity uses SHA-256 over the exact stored `data.json` bytes. The resulting digest and byte length are written to `manifest.json`.

Backup success requires this sequence:

```text
export D1
→ build data.json
→ SHA-256 data bytes
→ build manifest
→ upload data + manifest
→ read stored data back
→ recompute SHA-256
→ compare digest and byte length
→ verify counts/manifest
→ only then mark/catalog backup as valid
```

Provider-native checksums may be used as an additional transport integrity signal, but they do not replace the portable application-level SHA-256 contract.

## Restore safety sequence

A restore must follow this order:

```text
SA requests restore
→ first confirmation
→ second destructive-operation confirmation
→ server re-checks SA authorization
→ load manifest
→ verify appId / formatVersion / schema compatibility
→ load data
→ verify byte length + SHA-256 + record counts
→ create/retain a pre-restore recovery point when the current system supports it
→ execute controlled D1 restore transaction/sequence
→ post-restore reconciliation
→ audit success/failure
```

If any pre-restore verification fails, no destructive D1 write begins.

The exact D1 restore mechanics are deferred until the final relational schema is defined, but the safety sequence is fixed.

## Cross-application compatibility

CY Web and CYAccountingWeb should share the outer backup concepts and manifest vocabulary where practical, but `appId`, `schemaVersion`, payload entities, and restore logic remain application-specific.

A backup created for one application must never be offered as a restore candidate for another application merely because both use the same GCS project or BackupStorageProvider implementation.

## Future shared Backup Service

When the applications later move behind a shared CY Backup Service / Worker, this same split remains valid:

```text
App-specific BackupService adapter / exporter
        ↓
shared backup orchestration contract
        ↓
BackupStorageProvider
        ↓
GCS
```

The shared service may centralize object storage access, retention, cataloging, audit transport, and integrity verification, while application-specific export/restore adapters continue to own their schema semantics.
