# BD-025 — Legacy Desktop is the canonical workflow baseline; Legacy Mobile is incomplete

**Status:** CONFIRMED

## Decision

When reconstructing Legacy business behavior for CY Web, the Legacy **Desktop** implementation is the primary behavioral reference.

The Legacy Mobile implementation was stopped partway through development and contains older/incomplete business contracts. It must not be treated as an equal source of truth when it conflicts with Desktop behavior.

## Source precedence for Legacy behavior

For migration and workflow reconstruction, use this order:

1. current explicit user decisions;
2. confirmed CY Web Business Decisions;
3. Legacy Desktop HTML/JavaScript together with the shared GAS backend;
4. Legacy Mobile only as supplemental evidence where it does not conflict with the sources above.

A Mobile-only field, status, transition or validation rule must not be carried into CY Web merely because it exists in the old Mobile source.

## Examples of known divergence

The Order module already demonstrates why this rule is necessary. Legacy Mobile retains older concepts such as `待處理`, `修改後待處理` and an older `orderNo` path, while the later Desktop flow uses the coherent five-state work-order lifecycle:

```text
created / 已建檔
issued / 已出單
waiting_stock / 等到貨
picked / 已撿貨
shipped / 已出貨
```

The Desktop lifecycle, together with the shared backend and current user confirmation, is the migration baseline.

## New CY Web implication

CY Web will have one canonical data contract, permission model and business workflow for Desktop/Tablet/Mobile.

Responsive/adaptive presentation may differ by device, but business semantics must not diverge by viewport or device class.

Legacy Mobile remains useful for identifying old mobile UX ideas and historical compatibility shapes, but not as an independent business-rule authority.

## Audit implication

The Desktop-first review must include more than data fields. For every module it must inventory:

- state transitions and reversals;
- edit/delete lock points;
- role/permission checks;
- cross-module side effects;
- domain history/log behavior;
- centralized deletion audit behavior;
- structured ledgers and reconciliation logic.

This is necessary because several Legacy `history`, `logs`, `priceLog` and stock-log structures intentionally implement business traceability and must not be discarded as incidental JSON.
