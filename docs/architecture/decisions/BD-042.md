# BD-042 — Public WorkLog source provides configurable structure, not Chihyuan production parameters

**Status:** CONFIRMED

## Decision

The public Chihyuan Enterprise Management System source must provide the WorkLog/scoring feature as a configurable application shell. Chihyuan-specific production values are deployment/runtime data configured by an authorized Admin, not source-code defaults.

This applies to configurable WorkLog parameters including, where applicable:

- editing/work item/category names;
- scoring/reference points;
- descriptions and notes;
- custom/additional scoring rows;
- required/target average daily score;
- platform/channel lists;
- display order;
- active/inactive state;
- other organization-specific WorkLog configuration introduced later.

## Public source boundary

The public repository may contain:

- the generic WorkLog UI and configuration UI;
- schema/migrations required to store configuration;
- validation rules and APIs;
- generic category input modes such as checkbox versus quantity;
- add/edit/deactivate/reorder behavior;
- scoring/review mechanics;
- neutral examples or documentation placeholders when useful for development/testing, provided they are clearly non-production examples.

The public repository must not treat Chihyuan's actual production category names, scoring values, platform names, thresholds or other organization-specific parameters as canonical hard-coded application behavior.

Production configuration is created after deployment by Admin in the target environment.

Conceptually:

```text
Public source
  -> generic WorkLog/configuration capability

Deployment environment
  -> its own D1/config data
  -> Admin enters organization-specific WorkLog parameters
```

## Stable configuration identity

Configurable entries use stable internal IDs/keys. Business logic must not depend on a specific display label such as a Chihyuan category name.

For example, whether a category uses boolean selection or quantity entry is stored as configuration metadata (for example `input_mode`) rather than inferred from hard-coded names.

Renaming an Admin-configured category or platform must therefore not break historical relationships.

## History behavior

Historical WorkLogs retain the category/platform/scoring snapshots or stable references required to reproduce the historical record. Later Admin configuration changes must not silently rewrite finalized WorkLog facts or scores.

BD-012 remains applicable: reviewed/finalized scores are historical results and are not retroactively recalculated from later scoring-configuration changes.

## Relation to public deployment policy

This decision applies the project's broader principle that public source contains reusable interfaces and application structure while Chihyuan production configuration/data remains environment-specific.

The same pattern should be used for other CY-specific configurable business parameters unless a value is genuinely part of universal application logic.

## Consolidation note

Before D1 schema freeze and WorkLog implementation, consolidate this rule into the WorkLog Data Dictionary, Settings/configuration model, migration/seed policy, deployment/bootstrap documentation and tests. Production seed data must not accidentally reintroduce Chihyuan-specific values into the public repository.
