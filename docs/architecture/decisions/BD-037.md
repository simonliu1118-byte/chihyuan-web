# BD-037 — CY Web reuses shared Identity roles and uses app-specific tags only for module access

**Status:** CONFIRMED

## Decision

CY Web does not create a separate account-role hierarchy that duplicates CYInvoice Cloud / shared Identity.

The shared Identity authority remains responsible for the common account and workspace identity contract, including the existing shared user / admin / super-admin semantics. CY Web must consume that contract through its Identity adapter/service boundary instead of redefining those roles locally.

CY Web-specific classifications such as `sales`, `staff`, `warehouse`, and `designer` are app-local tags used only to decide which CY Web systems/modules an ordinary shared user can enter.

## Separation of concerns

Conceptually:

```text
Shared Identity
├─ identity / employee / workspace membership
├─ credential / session / recovery
└─ shared account role semantics
   ├─ ordinary user
   ├─ admin
   └─ super admin

            ↓ stable shared identity reference

CY Web membership / app profile
└─ app tags
   ├─ sales
   ├─ staff
   ├─ warehouse
   └─ designer
       ↓
   CY Web module-entry access
```

The CY Web app tags do not promote or demote a user in the shared Identity system and must not be treated as replacements for the shared admin/super-admin roles.

## Initial CY Web permission scope

For the initial CY Web implementation, keep the permission model intentionally coarse and compatible with the Legacy operating model:

- app tags determine whether an ordinary user can enter a CY Web system/module;
- CY Web Admin UI may manage the app-tag/module-entry mapping as permitted by the shared Identity/admin rules;
- existing domain-specific workflow restrictions remain enforced by their own business rules;
- do not introduce a new fine-grained capability/RBAC matrix during the initial migration.

The implementation may support more than one CY Web app tag on the same ordinary user so module access can be the union of the assigned tags when operationally useful. This does not create a new global role hierarchy.

## Admin / super-admin boundary

CY Web must not invent or duplicate admin/super-admin promotion rules. Those semantics are inherited from the shared CYInvoice Cloud / future CYCloud Identity authority.

If the shared Identity implementation changes its admin-management rules, CY Web follows the shared contract rather than maintaining a divergent local copy.

## Security boundary

Although the initial authorization model is coarse, module-entry and protected admin operations must still be enforced server-side. Hiding a menu or button in the browser is only presentation and is not the authoritative permission check.

## Future evolution

Fine-grained RBAC/capability permissions may be added later if the real operating need justifies the extra complexity. That later work must extend the app-specific authorization layer without moving CY Web-only permissions into the shared Identity role model.

## Relation to existing project rules

This decision specializes `PROJECT_RULES.md` section 7:

- CY Web reuses CYInvoice Cloud/shared Identity for account authority;
- app-specific permissions remain inside CY Web;
- CY Web does not create a second competing Identity system.

Before D1 schema freeze, the Identity/permission sections of `BUSINESS_DECISIONS.md`, `CANONICAL_DATA_MODEL.md`, and the Data Dictionary must be consolidated to reflect this boundary.
