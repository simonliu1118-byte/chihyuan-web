# BD-027 — Outsourcing hard delete is allowed only before confirmed outbound

**Status:** CONFIRMED

## Decision

An outsourcing order may be hard-deleted only while it remains in:

```text
pending_outbound / 待出庫
```

Once a real outbound operation has been confirmed, the outsourcing order has already produced a physical/business stock event and must not disappear through ordinary hard delete.

This intentionally tightens the Legacy Desktop behavior, which allows some non-paid outsourcing orders to be deleted after stock activity as long as the implementation compensates the mutable stock balance.

## Confirmed outbound and later states

For any order that has reached:

```text
outbound / 已出庫
received / 已入庫
priced / 已計價
paid / 已付款
```

cancellation/correction must use explicit business reversal operations rather than deleting the whole entity.

The target behavior is:

- preserve the outsourcing order identity and original business history;
- preserve the original outbound/receiving/pricing/payment events;
- create explicit reverse/compensating events where stock or other business facts must be undone;
- append structured domain history/audit with actor and time;
- keep reconciliation possible after the correction.

If a downstream state has already occurred, the later business effects must be reversed in a controlled order or through an equivalent controlled cancellation workflow. The system must not erase the whole chain as if it never happened.

## Stock-ledger implication

A confirmed outbound stock movement must never be physically deleted merely because the outsourcing order is cancelled.

When outbound material must be returned/cancelled, the stock ledger creates a linked compensating reverse movement. This preserves both facts:

1. the material was actually sent out; and
2. that movement was later reversed/cancelled.

The resulting contractor balance is derived/reconciled from the original movement plus the compensating movement.

## `pending_outbound` hard delete

A `待出庫` order has not yet produced a confirmed physical outbound movement, so ordinary hard delete remains allowed subject to normal authorization and deletion audit.

Deletion must still produce structured audit identifying at least the actor, time and deleted outsourcing-order reference. Exact role-to-permission mapping remains part of the later authorization design.

## Cancellation end state

This decision does not yet freeze whether a cancelled confirmed-outbound order should ultimately:

- return to `pending_outbound`, or
- remain visible under a dedicated cancelled/voided state.

That UX/workflow choice may be decided when the complete outsourcing reversal flow is finalized. Regardless of the final status code, historical events and stock movements must remain traceable.

## Migration implication

Legacy historical records that still exist should retain their workflow/history facts during migration. Future CY Web behavior must not reproduce Legacy's ability to erase a post-outbound order after compensating only the current stock balance.
