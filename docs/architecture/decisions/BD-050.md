# BD-050 — CY Web and CYAccountingWeb share one portable backup contract and converge on CY Backup Service

**Status:** CONFIRMED

## Decision

CY Web and CYAccountingWeb use the same outer backup-package semantics, integrity rules, provider contract and future shared storage-service boundary.

The applications keep their own database/export/restore semantics, but they must not independently invent incompatible backup containers or provider APIs.

## Canonical portable backup set

The shared outer package is:

```text
<app-scope>/<backup-id>/
├─ manifest.json
└─ data.json
```

The target common outer manifest contract is named:

```text
format = CYBackupSet
formatVersion = 1
```

The common manifest contains at least:

```text
format
formatVersion
backupId
appId
appVersion
schemaVersion
createdAtUtc
sourceDatabaseEngine = d1
workspaceScope / tenant scope when applicable
recordCounts
totalRecordCount
dataObjectName
dataSha256
dataByteLength
```

`data.json` is application-specific portable data. CYAccountingWeb and CY Web are not required to have the same database tables or restore ordering.

The outer manifest must remain provider-neutral. It must not contain R2 bucket names, GCS bucket names, provider object generations, credentials, provider access tokens or provider-specific verification state.

Provider/copy state belongs in the application/shared backup catalog or audit record, not in the immutable portable package bytes.

## Export-once rule

For one logical backup operation:

```text
App exporter
    ↓ exactly once
BackupSet { manifestBytes, dataBytes, digests, backupId }
    ↓
store/verify on R2
    ↓ same bytes
replicate/verify on GCS when policy requires
```

GCS replication must not trigger a fresh D1 export. Retry must reuse the already-created backup set.

## BackupStorageProvider contract

The required provider-neutral contract remains intentionally small and compatible with the provider boundary already used by CYAccountingWeb V0.17:

```text
putObject(key, bytes, metadata)
getObject(key)
listObjects(prefix)
deleteObject(key, versionToken?)
```

Provider implementations normalize provider-specific object metadata into a common result shape. A provider-specific generation/version/ETag may be carried as an opaque optional `versionToken`, but application/domain code must not depend on GCS- or R2-specific deletion semantics.

Storage providers own only object-storage operations. They do not:

- export D1;
- decide application schema compatibility;
- authorize a human restore;
- perform D1 restore writes;
- define application retention policy;
- reinterpret accounting/business data.

## Application BackupService boundary

Each application retains an application-level `BackupService` (or equivalent domain service) responsible for:

- exporting its authoritative D1 data into portable `data.json`;
- creating the canonical manifest and digests;
- validating `appId`, `schemaVersion`, record counts and application compatibility;
- deciding whether a backup is eligible for restore;
- enforcing user/application authorization, including Super Admin restore restrictions;
- double-confirmation restore orchestration;
- application audit evidence;
- performing controlled restore into the application's own D1 database.

The application service does not contain R2/GCS HTTP/API details.

## Future CY Backup Service / Worker boundary

A future shared **CY Backup Service / Worker** becomes the infrastructure/storage orchestration layer:

```text
CY Web App BackupService --------┐
CYAccountingWeb BackupService ---+--> CY Backup Service / Worker
future CY apps ------------------┘          │
                                           ├─ app-scoped R2 provider
                                           └─ app-scoped GCS provider
```

The shared Worker owns:

- provider adapters;
- storing opaque backup-set objects;
- provider read-back verification of exact bytes;
- cross-provider replication;
- provider-specific retention execution;
- logical-backup / provider-copy cataloging;
- storage health/error reporting.

It does **not** own application database schema semantics or write application D1 data during restore.

## Dataset and credential isolation

Isolation remains mandatory even after a shared service is introduced.

During independent deployment:

- CY Web and CYAccountingWeb use separate R2 datasets/buckets or equivalent isolated bindings;
- CY Web and CYAccountingWeb use separate GCS datasets and separate least-privilege service identities/credentials;
- one application's direct credential must not grant access to the other application's dataset.

After migration to the shared CY Backup Service:

- callers use a private/internal service boundary rather than public browser access;
- caller identity is mapped server-side to an allowed `appId` / dataset scope;
- the shared Worker uses separate app-scoped R2 bindings and separate app-scoped GCS credentials/configuration;
- the service must not use one broad credential merely for implementation convenience;
- an app cannot select another app's dataset by supplying a different `appId` string.

## Logical catalog model

One backup may have multiple provider copies. Catalog semantics should therefore distinguish:

```text
logical backup
  backupId
  appId
  createdAt
  manifest/data digest metadata

provider copies
  backupId + provider
  status
  verifiedAt
  storage key / opaque provider token
  last error
```

The UI should not present an R2 copy and a GCS copy of the same `backupId` as two unrelated backups.

## CYAccountingWeb V0.17 compatibility

CYAccountingWeb V0.17 production GCS backup is an accepted working baseline and must not be broken merely to adopt the shared contract.

Existing V0.17 backup sets remain readable/valid under a compatibility path. A move from its current application-specific outer format to `CYBackupSet` must be versioned and tested; old GCS objects are not rewritten in place.

The architecture migration is additive first, destructive cleanup last.
