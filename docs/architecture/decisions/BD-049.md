# BD-049 — Tiered backup uses R2 for daily operational recovery and GCS for cross-cloud disaster recovery

**Status:** CONFIRMED

## Decision

Chihyuan production backup is a tiered architecture:

```text
Cloudflare D1
    ↓ live authoritative database
canonical portable backup set
    ├─ Cloudflare R2  → daily operational backup / routine recovery
    └─ Google GCS     → lower-frequency cross-cloud disaster-recovery replica
```

D1 remains the live database. Neither R2 nor GCS is a live database or synchronization source.

This decision refines BD-045. GCS remains the cross-cloud/off-site disaster-recovery provider, while R2 becomes the primary operational backup store for routine daily recovery.

## One logical backup, multiple provider copies

A backup is identified by one `backupId` and one canonical portable backup set.

The application must **export D1 only once for a logical backup operation**. It must not export one payload for R2 and a second independently generated payload for GCS.

The exact same `data.json` bytes and `manifest.json` bytes are stored on each provider that receives that logical backup. Therefore:

```text
same backupId
same data.json bytes
same manifest.json bytes
same SHA-256
same byte length
same record counts
```

Provider-specific upload IDs, object generations, ETags, verification timestamps and errors are copy metadata; they do not change the portable backup-set bytes.

## Schedule

### R2 operational backup

- Scheduled once per day.
- Standard production execution time: **03:30 Taiwan time**.
- Every successful scheduled export targets R2.
- Operational recovery objective: latest verified R2 backup should normally be less than 24 hours old.

### GCS disaster-recovery replication

- Standard production replication days: **Wednesday and Sunday, Taiwan local date**.
- The eligible day's already-generated backup set is replicated to GCS after the R2 copy has passed read-back verification.
- No second D1 export is performed for GCS.
- This produces a normal cross-cloud disaster-recovery RPO of at most about four days while avoiding unnecessary duplicate export work.
- If a scheduled GCS replication fails, the system records the copy as pending/failed and retries from the verified portable backup set; it must not rebuild a different payload from D1 merely to retry the provider copy.

### Manual / high-risk safety backup

A user-authorized manual backup or pre-restore safety backup should request copies on **both R2 and GCS regardless of the weekday**, using the same canonical backup set.

## Retention

Application-level retention is provider-specific:

```text
R2   rolling retention = 30 days
GCS  rolling retention = 26 weeks (182 days)
```

R2 is intentionally shorter because it is the operational recovery tier. GCS is intentionally longer because it is the independent disaster-recovery tier.

Retention operates only on verified backup copies. Cleanup is best effort and runs after a new copy has been successfully stored and verified; cleanup failure must not retroactively invalidate a newly verified backup.

Provider-native lifecycle rules may be configured as a second safety guard, but they must use a longer threshold than the application policy and must not become the authoritative backup-validity mechanism.

A backup that is still required as the source of a pending cross-provider replication must not be removed by normal retention before that replication is resolved.

## Verification

Every provider copy is valid only after upload and provider read-back verification.

Portable verification includes at least:

- `data.json` byte length;
- `data.json` SHA-256;
- `manifest.json` byte length / SHA-256 where recorded by the implementation;
- `backupId`;
- application identifier;
- format/schema compatibility;
- record counts.

A valid R2 copy does not automatically imply that the GCS copy is valid, and vice versa. Copy status is tracked separately even though both copies represent the same logical backup.

## Restore preference

For ordinary in-application recovery while Cloudflare is operating normally:

1. prefer a valid R2 copy;
2. if the requested R2 copy is unavailable or fails verification, use a valid GCS copy of the same logical backup when available.

For Cloudflare-wide disaster recovery, GCS is the independent cross-cloud recovery source.

Restore authorization and D1 replacement semantics remain governed by BD-044 and the application-level `BackupService`; storage providers do not perform D1 writes.
