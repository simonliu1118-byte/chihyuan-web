# BD-034 — ERP data uses one fill/correct action with preserved correction history

**Status:** CONFIRMED

## Decision

CY Web uses one contextual action on a sales work order for the formal SMART ERP relationship.

Before ERP data has been completed, the button is labeled **回填 ERP 資料**.

After ERP data has been completed, the same button in the same location is relabeled **更正 ERP 資料**.

This is one business capability with two semantic modes, not two unrelated buttons or workflows.

## First fill

The first **回填 ERP 資料** operation completes the formal ERP relationship for the CY Web field/pre-ERP work order.

The ERP data includes at least:

- ERP customer number / formal customer binding;
- SMART ERP sales-order number.

Customer binding follows BD-031:

- a formal customer number must resolve exactly to an existing Customer master record;
- CY Web supplies the corresponding internal `customer_id` and Customer-master name;
- no fuzzy guessing, silent matching, or user-invented number/name combination is permitted.

When the first ERP sales-order number is successfully filled, the work order enters `issued / 已出單` according to BD-024.

## Correction

Once ERP data already exists, the same action becomes **更正 ERP 資料**.

Authorized internal staff may correct an incorrectly recorded ERP customer number and/or ERP sales-order number without treating the correction as an ordinary work-order content edit.

A correction does not require rolling the fulfillment state backward merely because the reference data was entered incorrectly. For example, a work order that is already `waiting_stock`, `picked`, or `shipped` may retain that lifecycle state while its ERP reference is corrected.

A correction is distinct from business cancellation. If the underlying order itself is being terminated, the existing **作廢工單** workflow applies instead of disguising cancellation as ERP-reference correction.

## History

ERP correction belongs to the existing Order domain history. Do not create a second redundant audit mechanism for the same semantic event.

A correction must preserve meaningful before/after values, including the fields that actually changed, for example:

```text
ERP 客戶編號: A00123 -> A00125
ERP 銷貨單號: SA26090088 -> SA26090091
```

The history event must also preserve actor and timestamp.

The Legacy behavior that logs only a generic `修改ERP單號` string is therefore strengthened so the prior and corrected references remain traceable.

## Permission

ERP fill/correction is an internal operational permission. The target CY Web permission model should authorize the capability explicitly rather than relying permanently on a Legacy hard-coded role string.

## UI rule

The user should not have to choose between separate "fill" and "correct" commands:

```text
no completed ERP relationship
    -> 回填 ERP 資料

ERP relationship already completed
    -> 更正 ERP 資料
```

The modal/panel may use the same fields and validation path in both modes; mode-specific copy and history behavior make the semantic difference explicit.

## Relation to previous decisions

- BD-024 defines the CY Web pre-ERP work-order lifecycle and first ERP handoff.
- BD-029 defines post-handoff hard-delete prohibition and explicit work-order voiding.
- BD-031 defines the simple Customer binding and no-guessing rule.
