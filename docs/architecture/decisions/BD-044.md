# BD-044 — In-app backup and restore are Super Admin-only with double confirmation

**Status:** CONFIRMED

## Decision

CY Web keeps in-application backup and restore as a supported product capability, but access is restricted to **Super Admin (SA)** only.

Regular users and Admin users must not be able to start a backup, browse backup versions for restore, or execute a restore operation.

## Restore confirmation

Restore is a high-risk destructive operation and requires two explicit confirmation steps before execution.

The second confirmation must clearly state that the selected backup will replace the current application data and that the operation is destructive / not directly reversible through ordinary UI actions.

A generic single confirmation dialog is insufficient.

## Server-side authorization and audit

The Worker/API must enforce SA authorization for backup and restore regardless of whether the UI hides the controls.

Each backup and restore operation must create structured audit evidence including at least:

- actor identity;
- timestamp;
- action type;
- selected backup/version identifier where applicable;
- result/status;
- request/correlation identifier where available.

Restore should also preserve enough metadata to identify the pre-restore state or the backup source used for the operation.

## Provider abstraction

CY Web source should depend on a generic backup provider contract (for example `BACKUP_PROVIDER`) rather than hard-coding Chihyuan production storage.

The concrete provider may be Cloudflare R2, Google Cloud Storage, or another approved deployment-specific backend. Resource identifiers, credentials, bucket names, tokens, and other production connection details are deployment-time configuration/secrets and must not be committed to the public repository.

This follows the existing public-source / deployment-injected infrastructure principle.

## Implementation sequencing

The product capability is confirmed now, but provider implementations may be delivered after the core D1 application and migration path are stable. The architecture should keep the provider boundary explicit so storage backends can be changed without rewriting the business UI or restore workflow.
