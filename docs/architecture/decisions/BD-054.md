# BD-054 — CY Web uses one shared in-App Audit Core with cost-conscious storage

**Status:** CONFIRMED

## Decision

Within CY Web, all modules must use one shared Audit Core / AuditService implementation for structured business-event audit.

Customer, Visit, Sales Work Order, Item/Defect, Outsourcing, WorkLog, Settings, Backup/Restore and future CY Web modules must not each create independent audit schemas, write paths, retention rules, or audit UI logic.

This decision is scoped to **CY Web only**.

CYAccountingWeb, CYInvoice and other separately developed CY Web Apps are not required to adopt this Audit Core at this stage. Cross-App consolidation may be considered later through a separate explicit decision.

## Shared-core responsibilities

The CY Web Audit Core should own the common contract for:

- recording an audit event;
- validating required event metadata;
- normalizing action/entity identifiers;
- optional before/after payload handling;
- querying/filtering audit events;
- concise timeline projection for normal business screens;
- detailed Audit Log projection for Admin/SA;
- retention/pruning support when a policy is later enabled.

Business modules provide the domain-specific event facts but do not implement separate storage/query mechanisms.

Conceptually:

```text
Customer -----------\
Sales Work Order ----\
Outsourcing ----------> CY Web Audit Core -> audit_events
WorkLog -------------/
Settings ------------/
Backup/Restore ------/
```

## Storage-cost principle

Audit is an accountability mechanism, not a full immutable copy of every business record.

The initial implementation must minimize D1 growth and downstream backup growth:

- ordinary CRUD does not create a new audit event on every save; it retains only last-modified metadata per BD-053;
- only meaningful business/domain actions create structured audit events;
- before/after data is stored only for fields where it materially improves traceability or another confirmed decision requires it;
- do not store full-row snapshots when a small field-level payload is sufficient;
- do not place attachments, PDFs, images, generated documents, large text blobs or binary content in audit payloads;
- concise front-end timeline and detailed Admin/SA Audit Log must use the same underlying event rather than duplicate event stores;
- avoid redundant derived text when stable action codes plus small metadata can generate the UI summary;
- secrets must never be written into audit payloads.

Because D1 backups include audit data, unnecessary audit growth also multiplies R2/GCS backup storage. Audit payload size is therefore an architectural cost concern, not merely a UI concern.

## Retention / pruning direction

The schema and Audit Core should support retention/pruning later, but the project does not yet set an arbitrary fixed retention period.

Before choosing a retention duration, production usage should first establish:

- actual event volume;
- average payload size;
- D1 growth attributable to audit;
- effect on R2/GCS backup size;
- operational need for historical investigation.

A future retention rule must preserve any audit evidence that another confirmed Business Decision explicitly requires to remain available.

## Relation to BD-053

BD-053 defines what is visible and what ordinary edits retain:

- normal CRUD: latest `updated_at / updated_by` only;
- meaningful business actions: structured audit;
- concise business timeline for ordinary users where useful;
- detailed Audit Log for Admin/SA.

BD-054 defines how that policy is implemented inside CY Web: one shared Audit Core and one common event foundation, with storage cost controlled from the start.
