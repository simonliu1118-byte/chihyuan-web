# BD-053 — General edits keep only last-modified metadata; detailed audit is Admin/SA-only

**Status:** CONFIRMED

## Decision

CY Web separates ordinary record-maintenance metadata from business/audit event history.

### Ordinary CRUD / master-data maintenance

For ordinary edits such as Customer basic information, phone/address/contact maintenance, Visit text changes, notes and similar day-to-day corrections, the initial system does **not** need to preserve a field-by-field change history or one audit event per save.

The current record keeps only the normal creation/update metadata needed for accountability and optimistic concurrency, for example:

```text
created_at
created_by
updated_at
updated_by
revision
```

For these ordinary edits, `updated_at` / `updated_by` represent the **latest** modification only. The application does not need to retain every previous editor/time or before/after field values.

## Business/domain actions

Actions that materially change workflow state, authorization, stock, formal-document status, review state, ERP handoff information, pricing/payment state, restore state, or other important business facts continue to produce structured audit/domain events.

Examples include:

- Sales Work Order ERP-number fill/correction, issue/pick/ship/void/reversal actions;
- Outsourcing outbound/receiving/pricing/payment and controlled reversal/correction actions;
- WorkLog submit/withdraw/review/cancel-review;
- Defect status changes/reopen;
- permission/access configuration changes;
- important Settings/scoring/configuration changes;
- backup/restore high-risk actions.

Not every such event requires a complete row snapshot. The event stores the minimum evidence needed to explain the business action. Before/after values are included only where they materially improve traceability or are required by another confirmed decision.

BD-051 remains an explicit example: WorkLog cancel-review requires an audit event for the action and status transition, but does not require retention of the cancelled score payload.

## Front-end visibility

The normal business UI may show a **simple human-readable history/timeline** for relevant domain actions, such as:

```text
2026/09/27 14:20  王○○  取消審核
2026/09/27 15:05  李○○  回填 ERP 單號
2026/09/27 16:10  陳○○  確認出貨
```

Regular users who are allowed to view the underlying business record may see this concise operational history where it is useful.

The normal UI does not expose raw audit payloads, technical metadata, request/correlation identifiers, or detailed before/after structures.

## Central Audit Log interface

Detailed audit inspection is provided through a separate **Audit Log / 紀錄** interface restricted to **Admin and Super Admin**.

This interface may provide:

- entity/module;
- business record identifier/reference;
- action;
- actor;
- timestamp;
- status transition;
- relevant before/after values when recorded;
- request/correlation metadata where useful for investigation;
- filtering/search by date, actor, module, action and record.

The Audit Log is primarily an investigation/administration tool, not part of ordinary end-user workflow.

## Storage model direction

A single structured `audit_events` foundation may back both:

1. concise domain-history presentation in normal business screens; and
2. detailed Admin/SA Audit Log inspection.

The application should avoid maintaining two independent duplicate event stores merely for the two presentations.

Candidate fields remain conceptually:

```text
id
entity_type
entity_id
action
actor_employee_id
occurred_at
summary
request_id / correlation_id
before_json   nullable
after_json    nullable
metadata_json nullable
```

Exact physical column names may be refined in the Final Data Dictionary.

## Sensitive-data rule

Audit payloads must not store plaintext passwords, session tokens, API secrets, backup credentials or equivalent secrets in before/after or metadata fields.

## Relation to BD-043

BD-043 already requires structured audit for configuration changes and defines Admin/SA authority. BD-053 adds the presentation/access rule: ordinary users receive only concise business history where applicable, while the detailed cross-module Audit Log is restricted to Admin and Super Admin.
