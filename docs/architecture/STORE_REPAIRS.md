# 門市售後維修契約

門市第三個業務頁籤「售後維修」（V0.9.69 起；維修單照片 V0.9.70）。規格來自 WO-0.9.69／WO-0.9.70 與 Claude 審查修正，工作單原文見 [2026-11-03 固定快照](https://github.com/simonliu1118-byte/chihyuan-web/tree/4cbc554a08c7fdf47a4140c7b9d912f61ce42c10/docs/development/work-orders)。本文件是現行契約；發布狀態看根 `TODO.md`。

## 權限與位置

- 頁籤排在「門市訂購」之後。Module Access 代碼 `STORE_REPAIRS`（「門市售後維修」），沒有權限就不顯示頁籤，API 也拒絕。
- 前端 `src/runtime/modules/StoreRepairs.tsx`；API `worker/http/store-repair-routes.ts`，根路徑 `/api/business/store/repairs`；共用常數與判斷在 `shared/store-repairs.ts`。

## 一張維修單

- 一張維修單只有一個品項。
- 欄位：
  - 送修日期：必填，預設今天。
  - 客戶編號：選填，最多 40 字。
  - 客戶名稱：必填，最多 40 字，可選稱謂「先生／小姐」。
  - 聯絡電話 1、聯絡電話 2、LINE 名稱：三者至少填一，元件與門市訂購相同。
  - 送修產品：五選一（低周波、薰蒸機、紅外線、電熱毯、其他），選中項目的文字必填。前四項的文字是型號；「其他」的文字是產品名稱。清單顯示為「低周波 HC-0502」，「其他」只顯示文字。
  - 產品機號：選填，最多 60 字。
  - 故障狀況：必填，最多 300 字。
  - 購買日期：選填，可勾「無日期」。
  - 配件備註：選填，最多 300 字。
- 項次 `list_sequence` 在 INSERT 內取號，同時新增兩張不會撞號。

## 處理流程

| 狀態 | 意義 | 登記內容 |
| --- | --- | --- |
| `RECEIVED` 收件 | 新增維修單 | — |
| `INSPECTED` 已檢測 | 門市初步檢測 | 日期、無異常／異常；異常必填問題說明（最多 200 字） |
| `SENT` 送廠維修 | 寄給廠商 | 日期、物流、寄送編號 |
| `REPAIRED` 維修完成 | 廠商修好寄回、門市收到 | 日期 |
| `NOTIFIED` 通知 | 已通知客人 | 日期 |
| `RETURNED` 機器歸還 | 客人取回，結案 | 日期、自取／寄送（寄送時同樣選物流） |

- 檢測「無異常」時，送廠與完修畫斜線（不適用），可直接通知。
- 只有確定略過的步驟才畫斜線，尚未走到的步驟不畫。
- 每個里程碑欄完成後顯示日期，點日期可更正；下一步顯示「登記」。每個日期對話框都可勾「無日期」。
- 物流：自送、郵局、新竹、大榮、黑貓（代碼 `SELF/POST/HCT/KERRY/TCAT`）。非自送時寄送編號必填；自送時該欄改稱「註記」，可空白。送廠與歸還共用同一個元件 `StoreShippingFields`。
- 歸還（結案）後 5 分鐘內可撤回，回到結案前狀態。這段猶豫期與門市訂購共用同一套判斷。
- 退回上一步、修改（檢測後修改要選修改理由）、操作紀錄都與門市訂購相同，並共用同一組元件與後端函式。

## 取消維修

- 任何未結案階段都可取消，必選理由：顧客不修（費用考量）、無法維修、顧客取回、其他（必填補充）。
- 取消**不結案**，機器仍要還給客人：
  - 處理狀態顯示灰色「取消維修」。
  - 取消時尚未檢測的單，檢測畫斜線。
  - 取消時尚未送廠的單，送廠和完修畫斜線。
  - 已送廠、尚未完修的單，保留「完修」步驟，代表從廠商收回機器；收回後才能通知。
  - 之後照常「通知 → 機器歸還」，歸還時結案。
- 通知之前可以撤回取消；通知之後不能撤回。
- 清單篩選有「取消維修」，看得到還沒歸還的取消單。

## 逾期

- 送廠超過 30 天仍未完修（`STORE_REPAIR_FACTORY_OVERDUE_DAYS`）：顯示「逾期未修回」。
- 通知超過 14 天仍未歸還（與門市訂購同一個 14 天常數）：顯示「逾期未取」。
- 逾期列淡紅底，篩選列有「逾期」。

## 清單

- 欄位：項次、處理狀態、送修日期、客戶姓名、聯絡電話／LINE、送修產品、產品機號、故障狀況、檢測、送廠、完修、通知、歸還、操作。故障狀況過長時省略，滑過顯示全文。
- 搜尋：客戶編號、姓名、電話、LINE、產品型號、機號、故障狀況、寄送編號。
- 篩選：處理狀態（共用 `StatusFilter`）與「顯示未結案」（共用 `OpenOnlyToggle`）。
- 清單一次最多 500 筆，與門市訂購相同。

## 維修單照片（V0.9.70）

- 每張維修單最多 3 張（`STORE_REPAIR_PHOTO_LIMIT`）。任何階段都可上傳，結案後也可補傳。
- 手機可直接拍照，電腦可選檔。
- 前端先縮圖並轉 JPEG：長邊最多 1600px、品質 0.8、不轉灰階。縮圖後仍超過 1 MB 就拒絕，請重新拍攝。人事附件共用同一個函式 `src/ui/forms/photo-upload.ts`。
- 後端只收 JPEG，大小不超過 1 MB，長邊不超過 2000px；與人事附件共用 `worker/files/jpeg-upload.ts`。
- 照片檔存在既有 R2 binding `HR_FILES`，路徑 `store-repairs/<維修單id>/<uuid>.jpg`；D1 只存紀錄（`store_repair_photos`）。
- 讀取照片要有 `STORE_REPAIRS` 權限，回應帶 `cache-control: private, no-store`。
- 刪除時 R2 檔案一起刪除；上傳和刪除都記入操作紀錄與 Audit。
- 清單「送修產品」旁顯示相機圖示與張數，點開照片對話框；操作欄不另加按鈕。

## API

根路徑 `/api/business/store/repairs`，權限 `STORE_REPAIRS`。

| 方法／路徑 | 行為 |
| --- | --- |
| GET `/` | 清單 |
| POST `/` | 新增 |
| GET `/:id` | 單筆 |
| PATCH `/:id` | 修改欄位 |
| POST `/:id/status` | 推進、退回、取消、撤回取消、結案撤回 |
| PATCH `/:id/date` | 更正里程碑日期 |
| GET `/:id/history` | 操作紀錄，cursor 分頁 |
| GET／POST `/:id/photos` | 照片列表、上傳（body 為 JPEG） |
| GET／DELETE `/:id/photos/:photoId` | 取得、刪除照片 |

每個寫入都帶 `requestKey` 防重送、帶 `expectedVersion` 防並發覆蓋；資料、事件與 Audit 在同一個 D1 batch 提交。
