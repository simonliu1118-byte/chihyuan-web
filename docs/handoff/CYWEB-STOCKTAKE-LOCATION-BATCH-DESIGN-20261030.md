# CYWEB 庫存盤點改版設計規格：品號卡 × 儲位優先 × 批號明細

> 狀態：**Claude 審核完成，使用者已決定（§14），可依 §14.2 施工**。  
> 整理日期：2026-10-30。本文依當日使用者多輪討論之最終決定彙總。  
> 涉及：CYWEB（前端／Worker／D1）、CYERPAutoQuery（**現階段只查核與約束，不修改 QUERY**）。  
> 重要：**只建立設計文件，不修改任何功能程式、Migration、QUERY，不合併功能 PR、不部署。**

## 0. 一頁摘要／最終使用者需求

- **一個品號＝一張手機精簡卡**；無論 ERP 原本因儲位、批號拆成幾個序號，WEB 仍只顯示一張該品號卡。
- 現場操作順序：**找品號 → 選儲位 → 找批號 → 輸入數量**；不要求先操作 ERP 原始序號。
- 同一品號有多儲位、多批號時，**以儲位為操作主軸**；每個儲位有自己的批號列表與可直接編輯的數量。
- 手機「選擇儲位」標題**最右方放「修改」按鈕**，修改目前選取的儲位；**已選儲位後，不再重複顯示「儲位 1324」標題**。
- 儲位選擇下方**直接**顯示各批號的數量輸入列：每一列左側顯示「批號 20250301」，右側輸入框及小字單位。**整條「批號／初盤數量」欄位標題及其分隔線全部刪除**。這項是使用者特別重申的要求，不得重新加回。
- 卡片邊框依**整個品號所有必要盤點格**判定：0 個已填維持一般邊框；部分已填為**黃色**；全部已填為**綠色**；填入數字 0 視為已填。
- 每個選定儲位內直接提供**「新增批號」**，因為可能有入庫但原 ERP 底稿尚未列出的批號。
- **WEB 可以修改儲位資料**；但**由 QUERY 將儲位變更回填 ERP** 必須列為獨立 **TODO**，在 QUERY 經技術驗證前不得宣稱 ERP 儲位已改好。
- 單一儲位 ERP 列正常顯示／盤點／寫回；遇到字串 `1324;3133` 時，WEB 分別盤點各儲位、**同一 ERP 原始列數量加總，按原 ERP 序號最多寫回一次**；差異判斷以加總為準。
- 不要恢復先前已移除的「儲位（手機一次顯示一組）」**全頁下拉篩選**。本設計的新儲位選擇，是**品號卡內的局部切換**，兩者不同。
- 桌機與手機使用同一個資料與權限模型；桌機以**品號、儲位分組的可編輯表格／區塊**呈現；手機則每品號一張卡。

## 1. 決策與範圍

### 1.1 使用者已確定的 UI 決策（不可擅自變更）

| 項目 | 最終決定 |
|---|---|
| 手機卡片身分 | `(sheet_no, item_code)`，**每品號唯一一張卡** |
| 手機卡頂 | 第一行「品號 空格 品名」，下一行小字規格；品名、規格**過長自然折行**，不得省略號截斷 |
| 手機卡內儲位 | 「選擇儲位」右側「修改」；下方顯示可選的四碼儲位與其填寫進度，例如 `1324 2/2`、`3133 1/2` |
| 選定儲位後 | **不要**再顯示「儲位 1324／修改儲位」重複區塊 |
| 批號列 | 直接 `批號 20250301    [40] 盒`，下一列同格式；**沒有**「批號／初盤數量」標題、沒有其分隔線 |
| 新增批號 | 作用於**目前選取儲位**，放在該儲位批號列表底部 |

| 邊框 | 未填一般／部分黃色／全部綠色，依**品號所有儲位與必要批號**完成度計算 |

| ERP 寫回 | 輸出以**ERP 原始序號**為界線，按原始列加總、最多更新一次 |

## 3. 資料身分與不變條件

定義三層（切勿混淆）：

- **ERP 原始列（SourceLine）**：`sheet_no + seq / line_key`，包含某品號、某批號、原始 ERP 儲位字串、原始帳面數量，**ERP 寫回最小單位**。同品號、同批號也可能有不同 ERP 序號，不可僅用品號＋批號做唯一映射。
- **WEB 儲位盤點格（CountCell）**：`source_line_key + warehouse + location_code`，供一個 ERP 原始列中每個儲位分別記錄初盤／複盤數量、操作者、時間、版本、異動狀態。**盤點最小單位**。
- **品號操作卡／品號分組（ItemGroup）**：一張底稿內依 `item_code` 衍生的**檢視模型**，整合多 ERP 原始序號與儲位；**不是**新的 ERP 列，不另建持久品號主檔。

必要不變條件：

1. 原始 ERP `seq`、`line_key`、`book_qty`、`batch`、`location` 原值要可回溯，且不可因前端改動而失真。
2. 類似 `1324;3133` 只拆成儲位盤點格，不會產生第二個 ERP 原始序號；單儲位 `1324` 也可統一建立一個盤點格，避免一套程式雙軌。
3. 一個 CountCell 的 0 是有效已填值；`null` 是未填。不得將未填當成 0 納入已完成判定。
4. 對每個 SourceLine，**所有必填儲位格填寫完成後**，才能得到其可確認的初盤／複盤合計；不能把部分合計當成完整合計。
5. 第一次主管確認：先計算每個 SourceLine 的已填加總，再用各 SourceLine 的 `book_qty` **只計入一次**，保留現有品號層級帳面／實盤比較。
6. ERP 寫回 payload：同一既有 SourceLine 對應最多一個 `seq` 和一個加總數量；現有 QUERY 不應收到多個相同 `seq` 的寫回命令。
7. 驗證／重試／回報錯誤必須仍可追到原 SourceLine；不得將前端卡片序號當成 ERP 序號。
8. 單位與庫別要有來源；一張品號卡內可能含多庫別、相同四碼儲位，要以**庫別身分＋儲位碼**內部識別、畫面作必要區分，不可誤合併。
9. 盲盤時 WEB 服務回傳仍不含帳面欄位，僅在主管首次確認後依既有權限顯示，不能靠前端隱藏敏感數量。

## 4. 必須支援的對照範例

假設 ERP INVR11：

| 原始 ERP 序號 | 品號 | 批號 | ERP 儲位字串 | 原帳面 |
|---|---|---|---|---:|
| 00017 | A00133 | 20250301 | 1324;3133 | 100 |
| 00018 | A00133 | 20250901 | 1324;3133 | 35 |
| 00019 | A00133 | 20261001 | 3133 | 10 |
| 00020 | A00200 | （無批號） | 1324 | 6 |

手機顯示 A00133 **只有一張卡**：

- 儲位 1324：批號 20250301 → 40；批號 20250901 → 15。
- 儲位 3133：批號 20250301 → 60；批號 20250901 → 20；批號 20261001 → 10。
- **不可**因為 A00133 有兩個儲位而製造兩張品號卡；但也**不可**製造原本沒對應關係的 `1324×20261001` 虛構必填格。
- 最後原序號 00017 合計 40+60=100、00018 合計 15+20=35、00019 合計 10；QUERY 分別最多寫回 00017、00018、00019 各一次。
- A00200 無批號，只在 1324 顯示「無批號」一個數量格；遵守原有無批號新增限制，不憑空建立新批號。

多庫別（同品號、同儲位碼）應在**同一品號卡**中區分儲位選擇鈕，例如「高雄門市 1324」和「其他庫別 1324」，不得僅看四碼合併。

## 5. 手機版：最終確認設計（嚴格依最後兩次 UI 修正）

### 5.1 一張品號卡的結構

```text
┌────────────────────────────────────────┐  ← 邊框依整品號進度變色
│ A00133 揚隆針灸針3405             3/4已填 │
│ 0.23mm*13mm/100入                     │
│                                        │
│ 選擇儲位                         [修改] │
│ [ 1324 · 2/2 已填 ] [ 3133 · 1/2 已填 ]│
│                                        │
│ 批號 20250301              [ 40  ] 盒  │
│ 批號 20250901              [ 15  ] 盒  │
│                                        │
│ [+ 新增批號]                 儲位小計55 │
└────────────────────────────────────────┘
```

以上以**選中 1324**為例，點 3133 後只替換下方的批號與數量區域，**整張卡仍是 A00133 那一張**，不清除 1324 的已填內容。

**特別禁止重新出現以下兩個先前已刪的 UI：**
- 「儲位 1324／修改儲位」重複標題列（修改按鈕已在「選擇儲位」最右方）；
- 「批號／初盤數量」表格欄標題及其上方分隔線。選儲位的下方**直接**是各批號數量列；「批號」字樣只出現在**每筆批號前面**。

### 5.2 排版／互動要求

- 品號與品名之間**一個空格**；第一行品號、品名可自然折行。第二行小字規格亦可自然折行，絕不硬切字或省略重要文字。
- 選擇儲位為**此品號局部切換**，可用同排或自動換行的按鈕（最小觸控範圍建議 44px）。已選狀態清楚，該儲位顯示 `2/2 已填` 等進度。
- 「修改」固定在「選擇儲位」標題最右側，僅對**目前選擇的品號＋庫別＋儲位**生效；禁止移動整個 ERP 底稿或其他商品。
- 批號與右側數量欄同一列；數量框右方有小字單位（盒、支等），高度 >=48px、字級 >=16px；數量編輯與焦點狀態沿用現有設計。
- 按鈕「新增批號」加在**目前選中的儲位**。儲位小計只代表該儲位已填值加總；若有未填必須保留未完成提示，不可以將小計誤稱完整庫存。
- 初盤顯示「初盤數量」語意、複盤顯示「複盤數量」語意，但**不要**在批號列表頂端加入獨立「批號／數量」標題列；可以用輸入欄位無障礙標籤或在卡片合適位置以極簡方式說明當前階段。
- 修改紀錄、必要時刪除新增批號等次要操作可使用既有 Dialog／局部展開，不要重新長出先前被嫌太大的全欄位卡。
- 卡片縮放 320／375／390／430px、iOS Safari 鍵盤、長規格、多批號與長品名時，內容可以增加高度，但**不可整頁橫向溢出**。
- ERP 儲位碼為四碼字串，`0032` 要保留前導零；多儲位原始字串按分號拆出後，儲位選擇鈕單獨顯示四碼。

### 5.3 卡片邊框與完成度

以當前階段該**品號所有需要填寫的 CountCell** 計算：

| 已完成 / 必填 | 卡片邊框 | 說明 |
|---|---|---|
| 0/N | 現有一般邊框 | 都尚未填寫 |
| k/N，0 < k < N | 黃色邊框 | 部分儲位／批號已填 |
| N/N | 綠色邊框 | 該品號全部必填格已成功保存 |
| N=0 或資料異常 | 一般／異常提示 | **不可**誤判綠色 |

- **0 算已填，null 才算未填**；輸入中尚未儲存成功時，不能先將狀態標為永久完成。
- 新增批號／新儲位後重新計算 N，原本綠色可能轉回黃色。
- 初盤與複盤**分別**計算；複盤中已經按品號帳面相符而鎖定的原 ERP 列，應視為「已核對」而非「必須重新填複盤」；其餘需複盤的格獨立計算。
- 卡片色彩不能是唯一訊息，還要保留小字 `3/4 已填`；與既有 CSS 變數／狀態色系相容。
- 儲位按鈕的 `2/2` 只統計被選的**該品號、該庫別、該儲位**，不是整張盤點單。

### 5.4 儲位切換、修改與新增

- 首次打開卡：建議優先選擇**第一個未完成的儲位**；如都完成則選第一個可用儲位。切換時未提交的輸入應先存檔／阻止切換／明確警示，**不得**靜默丟失。
- 「修改」開共用 Dialog，顯示原儲位／新儲位；儲位必須符合 `^[0-9]{4}$`，保留前導零；應顯示「此修改只更新 WEB，ERP 儲位尚未同步」。
- 同品號＋庫別內若目標儲位已存在，**不可**無提示合併，須拒絕或進入另行設計的安全合併流程；不可直接覆蓋已填數量。
- 儲位修改要保留**原 ERP 儲位**和**WEB 目前儲位**及歷史；即使顯示改成 1325，原 ERP 1324 仍可追蹤。
- 新增批號：先核對**目前選定儲位**、品號、庫別是否對應既有 ERP 批號列；若是另一儲位已有的批號，優先連到**可明確唯一確認的原始 ERP 列**並新增儲位 CountCell；若是新批號才新增「ERP 新增列」的父資料。遇到同品號／批號有**多個** ERP 序號無法判定者，應阻止自動關聯並要求確認，不能任意取第一筆。
- 若新增某儲位／新批號會造成 ERP 儲位清單要變更，務必標記「ERP 儲位異動待處理」，依第 8 節的防護處置。

## 6. 電腦版：同一份分組資料、不同視覺呈現

- **品號作為大分組**：品號、品名、規格只需呈現一次；同品號原始 ERP 多列不再平鋪為使用者必須分別尋找的多筆。
- **儲位作為次分組**：同一儲位的各批號排列在其下；可採延續叫貨 `cy-ordering-grid` 樣式的跨列儲位欄或輕量可編輯群組。
- **批號作為每一個數量輸入列**，在所屬儲位內直接可填寫數量，末端有「新增批號」。
- 需要清楚提供**該儲位的「修改」入口**、品號／儲位完成度、數量儲存狀態；保留明細編輯、歷史、權限、版本衝突。
- 不恢復全頁儲位下拉，不犧牲原搜尋（品號、品名、規格、儲位、批號）。
- 桌面不一定需要手機的邊框狀態，但應以共用狀態樣式／進度提示反映品號與儲位完成度。
- 共用資料聚合函式、相同 CountCell 儲存 API；不要為手機與桌機分別維護不同盤點狀態。

## 7. 建議資料表／API 與遷移（**待 Claude 審核，不是已定案 schema**）

### 7.1 保留 ERP 權威父表，新增一張儲位數量表

保留 `stocktake_lines` 為 SourceLine（ERP 底稿原始列）。建議新增一張子表 `stocktake_location_counts`，**只有一張新子表**，不另建品號卡持久主表。概念欄位：

| 欄位 | 目的 |
|---|---|
| `id` | 穩定子列 ID，避免修改儲位碼時主鍵消失 |
| `sheet_no`、`source_line_key` | 關聯 ERP 原始列；FK 對應 `stocktake_lines` |
| `warehouse_identity` | 區分不同庫別，相同儲位碼不混合；需核對 ERP 有無穩定庫別 ID，不能只憑顯示名稱猜測 |
| `erp_location_code` | 匯入 ERP 時的原始四碼儲位，不覆寫 |
| `current_location_code` | WEB 顯示／盤點用儲位，可經使用者修改 |
| `first_qty`、`recount_qty` | 每儲位獨立數量，儲存十進位字串 |
| `first_by/at`、`recount_by/at` | 各儲位各階段操作者與時間 |
| `version`、`rev` | 子列 optimistic concurrency 與整張單增量更新 |
| `location_change_pending` | 標記仍需 QUERY 處理的 ERP 儲位異動 |

建議唯一性：同底稿＋原始 SourceLine＋同庫別＋**目前儲位**不可有重複活躍子列；但允許不同 SourceLine 在相同庫別／儲位各有自己的 CountCell，因為不同批號／ERP 序號必須保留。

需決定是否延伸 `stocktake_line_history` 支援 `location_count_id`／儲位修改操作，或新增獨立 history 表。歷史必須能追蹤每次數量與儲位修改，且刪除／修改不消失。

### 7.2 父表的初盤／複盤合計

建議：
- 原 `stocktake_lines.first_qty`、`recount_qty` 當成每個 SourceLine 對應子表的**已完成合計投影**。
- **只有該 SourceLine 所有必填子列均非 null，合計欄位才非 null**；否則維持 null，避免半成品被認為完整。
- 同一 D1 原子交易內，驗證子列版本 → 寫入子列 → 根據**最新子列表**重新計算父列合計 → 更新父列／sheet 版本、統計及審計，避免甲乙分別填不同儲位時互相覆蓋。
- 用現有 `parseStocktakeQuantity`／`decimalStocktake` 的定點處理；不可 JavaScript 浮點加總後寫回 ERP。
- `stocktake_sheets.total_lines`、`counted_lines` 仍是**ERP 原始列**語義，不能因拆出多個儲位而增成兩倍；品號卡另以 CountCell 數量顯示 `3/4`。

### 7.3 推薦 API 方向

- GET 盤點詳情：保留既有 `sheet / lines`，在每 SourceLine 之下增加 `locationCounts` 或同一回應的關聯子列陣列（以穩定 ID 對應）；初盤的 `bookQty` 不得因新 API 洩漏。
- PATCH 儲位數量：傳 `sheetNo + locationCountId + quantity + expectedVersion`，後端必須確認 child 所屬 sheet、phase、鎖定及權限；保留 per-child 衝突提示。
- PATCH 儲位編號：傳目前選的品號／庫別／儲位身分及 version；後端**同一交易**重命名該品號此儲位下關聯的所有批號子列，保留原始 ERP 儲位、寫 history、標 pending；不能改到其他品號。
- POST 新增批號：帶選定儲位身分，查既有 ERP 批號關係或建立新增父列，再建立指定儲位子列；避免只用 `itemCode+batch` 推測 ERP 身分。
- 必須支援增量同步：子列改動通知目前的 10 秒 detail polling／版本更新；不能因為父列未變而漏更新另一個儲位。
- 錯誤回應要區分：欄位已修改、儲位重複、ERP 序號關係不明、工作階段不允許、待 ERP 儲位異動等。

### 7.4 舊資料遷移與同步不覆蓋

- **未填的舊 ERP 列**：由原始 location 按分號建立 CountCell（`1324` → 1 子列；`1324;3133` → 2 子列）。需做可重跑、具唯一性保護的 idempotent backfill。
- **已填的單一儲位列**：可將現有 `first_qty`／`recount_qty` 原樣搬入該唯一子列，保留歷史／版本。
- **已填的多儲位列**：原本只有合計，**無法知道各儲位分量**；絕不能自動 50/50、全部塞第一儲位或其他猜測。建議標記 `LEGACY_UNALLOCATED` 待主管受控處理，保留合計及舊紀錄，未解決前阻止誤確認；由 Claude 決定獨立處置流程。
- 已完結的歷史盤點單不應為追求新 UI 而改寫帳面、盤點值與 ERP 回填歷史。
- 現有 SYNC 若已有人填寫就不覆蓋；新子表建成後也必須將**任何子列已填寫**視為盤點進行中，禁止重新讀 ERP 覆蓋資料。
- 原 `1324;3133` 若有空格／重複／`;;`／非四碼，採嚴格解析與可見異常紀錄；**不可**靜默丟失儲位或自動亂配。

## 8. 主管確認、差異比較、QUERY 寫回與安全阻擋

### 8.1 初盤、複盤確認

1. 初盤必須所有**必填子列**已存成功，且沒有 unresolved legacy 或違規對應，才能首次確認。
2. 聚合每個 SourceLine `sum(child.first_qty)`，帳面 `book_qty` 仍對 SourceLine 計算一次。
3. 沿用既有「按品號加總對比帳面」的初盤確認規則，再決定 SourceLine 鎖定；**不得**拿每個儲位的 40、60 個別去跟原 ERP 的 100 比較。
4. 複盤對未鎖定 SourceLine 的相關子列再逐儲位／批號盤點；全部需複盤者完成才可二次確認；已鎖定的原始列沿用初盤合計。
5. 顯示各儲位小計與全品號進度，但帳面／差異只有初盤完成、權限允許後顯示。

### 8.2 ERP 寫回映射（本次必須保住）

- 同一原始 ERP 序號可能對應 2+ WEB 儲位 CountCell；**最後僅輸出一筆** `{key:source_line_key,seq:original_seq,itemCode,batch,quantity:sumOfRequiredChildren}`。
- 舊版 `stocktakeWriteRows`、主管確認與 QUERY payload 的入口應先做一層「已核實的 SourceLine 合計」；不得直接把卡片或子列當成 ERP 寫回列。
- QUERY 既有的 INVI14 寫入與 INVR11 回讀核對，原則上可繼續以原始 seq 使用；仍要做單儲位／多儲位／混合批號測試，不可未測即宣稱 ERP 全流程兼容。
- 多個 ERP 原始 seq 即使同品號同批號，仍必須分別結算與寫回，禁止被 UI 一張品號卡誤合併為一個 ERP 寫回 seq。
- 現有 INVI06 新增批號只確認了品號、批號與數量，**沒有經證明可指派新 ERP 儲位**。

### 8.3 修改儲位尚未支援 ERP 回填的安全界線（設計建議，請 Claude 重點審查）

- WEB 可存「原 ERP 儲位」與「修改後 WEB 儲位」，但必須明確標記 ERP 未同步。
- **建議最安全的暫行策略：可在 WEB 繼續盤點，但只要本張盤點單含未解決的 `location_change_pending` 或新增批號需指定 ERP 新儲位，就**阻止最終「二次確認→ERP 已確認」**，直到 QUERY 有已驗證的 ERP 儲位回填／核對機制，或經審核制定明確的例外流程。切勿自動清掉 pending 並顯示 ERP 儲位同步成功。
- 純原始儲位、原始 ERP seq 的一般數量寫回不受影響；若要允許「數量先確認、儲位後補」，需要明確分開數量確認與儲位同步狀態，不得沿用現有單一 `ERP_CONFIRMED` 讓使用者誤解。
- 建議在正式開發前先由 Claude 確認：產品／營運是否接受此 pending 阻擋，以及是否需給管理員取消未送出的 WEB 儲位修改；**不能自行放寬保護**。

### 10.1 資料／ERP 對應

1. 單儲位、單批號：跟目前一樣正常同步、填寫、首確認、複盤、寫回。

5. 同批號跨儲位：同一 batch 可在不同儲位輸入，不重複新增 ERP 批號列。
6. 同品號同批號不同 seq：不錯配寫回；模糊關聯必須報錯。

10. 0、null、四位小數、數量極值：精度與完成度正確，拒絕負數輸入。
11. 部分子列已填：原父列完成度仍未填／不可首確認；全部填完才合計。
12. 初盤品號帳面 vs 已填數量：按 ERP 原列帳面一次、再做品號加總；複盤僅未鎖定子列必填。

14. 兩人同時填不同儲位：互不覆蓋；同一格同版同時寫須產生明確版本衝突。
15. 舊未填與已填單儲位 backfill 正常；舊已填多儲位不自動分配。
16. 已開始盤點時重新 SYNC 不能重建子列／擦掉儲位數量。
17. ERP 失敗回覆／重試：不會重複更新同 seq、不可丟失未完成資料。

### 13.1 對 §12 問題的回覆

1. **永不重複寫回／帳面只算一次**：成立，前提是寫回只從 `stocktake_lines`（原始列）產生，每列一筆，數量＝該列所有儲位格的合計。`(sheet_no,seq)` 已有唯一鍵，再加一條寫回前檢查：payload 內 seq 不重複，否則整批拒絕。帳面只存在原始列，儲位格**不存** `book_qty`。
2. **子表身分**：用穩定 `id`，加唯一鍵 `(sheet_no, source_line_key, warehouse_name, location_code)`。庫別目前只有 `warehouse_name`（INVR11 匯出字串），同一張底稿內穩定，就用它，不另造庫別 ID。
3. **D1 並發**（最重要的修正）：**不要把合計寫回父列**（§7.2 的「投影」）。兩人同時改同一原始列的不同儲位，各自重算父列一定會互相覆蓋，要防就得在父列加版本鎖，衝突會很頻繁。改法：
   - 數量只存在儲位格，各格自己的 `version` 做樂觀鎖。
   - 合計在**主管確認與建立寫回工作時**由 Worker 一次讀出全部儲位格計算（確認本身是單一動作，在同一 batch 用 sheet `version` 守門）。
   - 完成度（`3/4`）由前端從儲位格算，`stocktake_sheets.counted_lines` 改為計「已填儲位格數」（`total_lines` 同步改計儲位格數）。這裡改變了原本「原始列」的語義，但只有清單上的進度數字在用，影響可控。
   - 儲位格的數量存 **TEXT 定點字串**，與父列一致，沿用 `parseStocktakeQuantity`／BigInt 加總，不在 SQL 加總。
   - 儲位格要有 `rev`（與父列同機制），讓 10 秒的增量輪詢（`rev>?`）照常只讀變動列。
4. **複盤範圍**：沿用「品號加總相符就鎖定」。被鎖定品號底下的原始列與其儲位格，複盤階段都不需填寫，不計入複盤的 N；品號卡顯示「已核對」。未鎖定品號的**所有**儲位格都要複盤。
5. **舊資料**：盤點功能 10/29 才上線、真 ERP 測試還沒開始（等 CYERPAutoQuery 1.3.0）。實作前先唯讀查正式 D1：
   - 「已填數量且儲位含分號」的列，**沒有**：migration 直接拆儲位格並搬入既有數量（單儲位列搬原值；多儲位且未填的列建空格）。
   - 若有：migration 要擋住失敗，不做 `LEGACY_UNALLOCATED` 流程，改請使用者決定清空重盤或另處理。
   
   這樣可以省掉整套 legacy 流程。
6. **QUERY 相容**：INVI14／INVR11 以原始 seq 寫回與核對，父列層級不變，所以 QUERY **不用改**。INVI06 新增批號沒有儲位能力，所以新增批號一律落在「ERP 預設儲位」，見 §13.4 (C)。
7. **儲位修改與 ERP 同步**：見 §13.4 (B)，建議不擋二次確認。
8. **UI**：§5 的規格清楚，Phase 2 實作時逐條對照 §10.2 #20–#22 的禁止項；我審查時會照這三項檢查。
9. **成本**（D1 Free）：儲位格約為原始列的 1～1.3 倍；增量輪詢只讀變動列，成本接近現況。全量重載多讀一次儲位格表，可接受。

### 13.2 建議切片（取代 §11 Phase 1–2 的內容）

- **第一刀（必要）**：
  - 新表 `stocktake_location_counts`，不含 `current_location`／`location_change_pending`。
  - SYNC 時依分號拆儲位格；舊資料依 13.1-5 處理。
  - 儲位格 PATCH API；確認與寫回改從儲位格合計。
  - 手機每品號一張卡＋儲位切換＋批號數量列＋三色邊框；桌面依品號／儲位分組。
  - 不含「修改儲位」，「新增批號」維持現行（無儲位）。
- **第二刀（可選）**：「修改儲位」與「新增批號指定儲位」，依 §13.4 (B)(C) 的選擇實作。
- **第三刀（獨立 TODO）**：QUERY 回填 ERP 儲位、重新盤點流程（§9 TODO A／B）。

### 13.3 對 §7 的其他修正

- `location_code` 嚴格解析：`^[0-9]{4}$`，用分號分隔，去前後空白；重複或格式錯誤時，該列標成同步錯誤並顯示在同步結果，不靜默丟棄。實作前先用真 INVR11 樣本確認儲位真的都是四碼。
- 歷史：`stocktake_line_history` 加 `location_count_id` 欄位（可為 null），不另建表。
- 新 migration 編號 **0032**（已有兩支 0031）。

### 13.4 需要使用者決定

- **(A) 多儲位原始列在單儲位盤點的必要性**：若現場「一個批號同時放兩個儲位」很少見，第一刀可以讓 `1324;3133` 這種列在卡片中顯示為一個「1324+3133」合併儲位、只填一個數量，就不需要拆格。這樣**整個子表都可以不做**，改動只剩 UI 分組。建議先看真 INVR11 資料中分號儲位的比例再決定。
- **(B) WEB 修改儲位、ERP 未同步時**（第二刀）：
  1. 擋住二次確認，直到 QUERY 能改 ERP 儲位：最安全，但 TODO A 完成前，有改過儲位的盤點單都無法寫回 ERP。
  2. 數量照常寫回 ERP，儲位修改另列「ERP 儲位待手動修改」清單，管理員在 ERP 手動改完後勾選完成。**建議這個**：不卡盤點，也不會誤稱 ERP 已改。
- **(C) 新增批號指定儲位**：INVI06 只能填品號、批號、數量。可選擇：
  1. 新批號只記 WEB 儲位，ERP 由人工指定，併入 (B)2 的清單；**建議這個**。
  2. 暫不允許在多儲位品號新增批號。

## 14. 使用者決定與施工範圍（2026-10-30，取代 §11 與 §13.2 的未決部分）

### 14.1 使用者決定

- **舊資料不遷移**：migration 0032 清除既有盤點底稿資料（`stocktake_sheets`、`stocktake_lines`、`stocktake_line_history`），**保留** `stocktake_sync_ignored` 與 Audit；上線後使用者重新執行「同步 ERP」。真 ERP 寫回尚未開始，沒有需保留的已寫回資料。不做 `LEGACY_UNALLOCATED`。

- **(B) 選 2**：WEB 修改儲位不擋二次確認；數量照常寫回 ERP，儲位修改進「ERP 儲位待手動修改」清單，管理員在 ERP 改完後勾選完成。
- **(C) 選 1**：新增批號可指定 WEB 儲位，ERP 端由人工指定，同樣進上述清單。

### 14.2 施工範圍（給 GPT）

**第一刀：資料與分儲位盤點**

1. Migration `0032`：
   - 建 `stocktake_location_counts`：`id` INTEGER PK、`sheet_no`、`source_line_key`（FK `stocktake_lines` ON DELETE CASCADE）、`warehouse_name`、`location_code`（`^[0-9]{4}$`）、`first_qty`／`recount_qty`（TEXT 定點，與父列同格式）、`first_by/at`、`recount_by/at`、`version`、`rev`。
   - 唯一鍵 `(sheet_no, source_line_key, warehouse_name, location_code)`；`(sheet_no, rev)` 索引。
   - 清除既有盤點底稿資料（見 14.1）；`stocktake_line_history` 加 `location_count_id`（可 null）；表與欄位登記到 `schema-columns.ts`、`validate_schema.py`、可攜備份。
2. SYNC：每個原始列依分號拆出儲位格；儲位碼不合法或重複時，該底稿同步失敗並回報原因，不靜默丟棄。無儲位的列建立一個 `location_code` 為空字串的格（需調整 CHECK 允許空字串，或另以 `0000` 表示並在 UI 顯示「未指定儲位」，二選一並在 handoff 說明）。
3. API：
   - 數量 PATCH 改以 `locationCountId + expectedVersion` 更新儲位格，`rev` 走現有增量輪詢；GET 詳情回傳儲位格，初盤時仍不含帳面。
   - 父列 `first_qty`／`recount_qty` 不再寫入（§13.1-3）。
   - 主管確認與建立寫回工作時，由 Worker 從儲位格加總（BigInt 定點）；任一必填格為 null 就拒絕；payload 每個原始 seq 只一筆，寫回前檢查 seq 不重複。
   - 複盤：品號鎖定規則不變，鎖定品號的儲位格不必複盤。
   - `counted_lines`／`total_lines` 改計儲位格。
4. UI：
   - 手機：每品號一張卡＋儲位切換＋批號數量列＋三色邊框，完全依 §5，含禁止項。
   - 桌面：品號／儲位分組，依 §6。
   - 「新增批號」作用於選定儲位：既有批號在其他儲位時，新增該儲位的格；全新批號沿用現行 INVI06 新增列，再建該儲位的格。
5. 測試：§10.1 #1–6、#8–12、#14、#16–17 與 §10.2 全部。

**第二刀：修改儲位與待手動修改清單**

- 「修改」：改目前品號＋庫別＋儲位下所有儲位格的 `location_code`。保留 ERP 原始儲位（建格時另存 `erp_location_code`），目標儲位已存在時拒絕，並寫歷史。
- 「ERP 儲位待手動修改」清單（盤點頁內，管理員可見）：列出 WEB 儲位與 ERP 原始儲位不同的格，以及指定了儲位的新增批號。管理員在 ERP 改完後勾選完成並記 Audit。這份清單不影響二次確認與寫回。

**不做**：QUERY 改 ERP 儲位、重新盤點（§9 TODO A／B）。
