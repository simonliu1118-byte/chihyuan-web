單一表格、單列表頭，不用每筆卡片；一列代表一筆顧客訂購，保留多品項在同儲存格分行列出，不複製成多筆訂購。

|---|---|---|---|---|---|---:|---:|---|---|---|---|---|---|
| 訂購 | 2026/10/31 | 合成示例甲 | 測試電話 | — | 測試商品 ×2 @100 | 200 | 0 | 顧客需求 | [→] | — | — | — | 修改／取消／紀錄 |
| 叫貨 | 2026/10/30 | 合成示例乙 | 測試電話 | — | 測試商品 ×1 @300 | 300 | 100 | — | 10/31 | [→] | — | — | 修改／取消／退回／紀錄 |

- 備註在訂金右側；叫貨左邊加 2px 共用 border token 的粗直線，表頭、資料列都連貫，不額外增加一個空白欄。展開紀錄列可橫跨全表。
- 處理狀態在最前，使用既有 `StatusChip`（與盤點相同 pill），文字固定區分「訂購／叫貨／到貨／通知／取貨（結案）／取消」。顏色輔助，不能只靠顏色區分。
- 訂購資訊區：姓名電話等短值盡量單行，品項／備註可換行；備註過長限高並可展開完整文字，不能只能靠 hover 才讀到。
- 金額、訂金右對齊，狀態／進度日期置中。日期統一台北顯示；平時 YYYY/MM/DD，詳細時間在紀錄中。
- 保留搜尋、各狀態篩選與通知逾 7 天未取篩選，新增「訂購」篩選。搜尋增加備註。
- 操作欄使用緊湊圖示「修改／取消／退回／紀錄」，每個都有 title、aria-label 與可見焦點。取消危險色，紀錄可附筆數；不放重複的前進按鈕。

### 2.1 共用 UI 與寬度

沿用 `cy-ordering-grid-scroll`、`cy-ordering-grid`，新增門市訂購專用 class/colgroup；它們是目前盤點使用的共用 CSS 表格樣式，不是已有一個可直接套用的萬用業務 React 元件。工具列沿用 `DataViewToolbar`，篩選用 `StatusFilter`、彈窗 `Dialog`、欄位 `Field/FormSection`、確認 `useConfirmation`、錯誤回饋既有 provider。不能直接挪用盤點業務元件。

這次 14 欄客觀上比盤點寬：優先給品項／備註彈性寬度，進度欄固定緊湊寬度，避免靠極小字體塞入。寬桌面完整顯示；窄桌面允許共用容器內水平捲動（頁面本身不可溢出），固定狀態／姓名與操作欄需以真實寬度驗收，固定欄不得覆蓋內容。若要任何桌寬都無水平捲動，必須另確認隱藏 LINE 等欄位，不能擅自刪欄。

本輪主要設計桌面清單。顧客訂購手機現為卡片，建議保留外觀與觸控方式；新流程資料語意、理由與版本驗證兩端一致。此項不改盤點手機版，也不把 14 欄表格硬塞進手機。

## 3. 狀態、固定圖示與手動日期

正常路徑：訂購 → 叫貨 → 到貨 → 通知 → 取貨（結案）。取消是另外的終止結果。

### 3.1 每一步使用同一種圖示（使用者補充）

推薦固定使用「圓框右箭頭」SVG 圖示按鈕（示意 →），放在下一個進度欄中。同事只要找相同圖示就能推進該步驟；按鈕造型、尺寸與顏色一致，由欄位標題說明是哪一步。不使用每階段不同圖示，不再依不同文字猜操作。

| 目前 pill | → 按鈕位置 | 點擊後小日期選擇器標題 | 可退回 |
|---|---|---|---|
| 訂購 | 叫貨欄 | 叫貨日期 | 無 |
| 叫貨 | 到貨欄 | 到貨日期 | 訂購 |
| 到貨 | 通知欄 | 通知日期 | 叫貨 |
| 通知 | 取貨欄 | 取貨日期 | 到貨 |
| 取貨（結案） | 無 | 可點日期更正 | 通知（誤按更正，需理由） |
| 取消 | 無 | 本階段唯讀 | 本階段不提供恢復 |

- 同一列只提供下一步一個 →；未到達欄為 —。完成欄顯示日期，點日期可再開選擇器修改。
- 按鈕 aria-label／title 包含實際動作，如「登記到貨日期」，不能只有「下一步」。移除處理狀態下拉；不能點未來第二步跳階。
- 日期編輯與推進分開：修改日期只改該日期，不重新執行進度、不產生另一筆取貨／通知事件。

### 3.2 全手動操作與小日期選擇器（使用者明確指示）

- **本階段全部手動，不連動叫貨、ERP、LINE、簡訊、庫存或金流。** 按鈕只是人員登記已完成該步驟，不自動叫貨、通知或收款。
- 點 → 開啟錨定該格的小型日期選擇器（popover），有日期欄、儲存／取消。新增步驟預設台北今天，可改為實際作業日期；尚未儲存不改狀態。
- 日期必填，已登記日期**可以修改、不能清空**；不提供清除操作，空值、無效日期由前後端共同拒絕。取消視窗保留原狀，不寫日期或改進度。
- 點已登記日期會預填該日期；儲存修改後在歷程留下日期前後值、操作人、操作時間。結案仍可更正既有步驟日期，不因此解鎖品項／金額等訂購內容。
- 到取貨步驟仍採同一日期選擇器，標題「取貨日期」，儲存按鈕「儲存並結案」，清楚表達其結果，不額外堆疊重複確認視窗。
- 實際作業日存 YYYY-MM-DD；系統實際提交時間另外存 UTC timestamp 並以台北顯示，**兩者不可混用**。例如 11/02 補登 10/31 到貨，歷程應同時說明作業日 10/31、操作時間 11/02。
- 建議日期不得晚於台北今天，且訂購日 ≤ 叫貨日 ≤ 到貨日 ≤ 通知日 ≤ 取貨日（同日允許）。更正中間日期時檢查相鄰已知日期，不自動連帶改其他欄。此為待審核的防呆建議；歷史未知日期不能以虛構值擋住補登。
- 通知逾 7 天未取的提醒，改從目前有效的「通知作業日」按台北曆日計算；補登較早通知日可能立即出現逾期提醒，不能以今天操作時間重新起算。
- 到貨本階段代表整筆所有品項已到齊；部分到貨可先記備註，逐品項到貨另案。

### 3.3 與退回上一步相容

- 退回一次僅一步，建議理由必填；送出前顯示「從 X 退回 Y」。伺服器檢查相鄰狀態。
- **不因退回刪掉已登記日期**。被撤回步驟保留上次日期，標示「已退回」，在紀錄中留退回事件；該日期不再代表目前已完成的進度。這與「日期不能清空」一致。
- 再次前進時，下一步的 → 與已退回標示可並存；小日期選擇器預填上次登記日期，讓人員確認或修改，儲存後才恢復該步驟的有效狀態。
- 通知退回到貨時暫停未取提醒（狀態不再是通知），但不清除通知日；再次通知由人員確認／修改通知日後重新計算。結案退回通知保留原通知日，不藉此重置提醒。
- 需以狀態／事件有效性判斷已完成步驟，不能單憑日期非空判斷。取消保留日期與歷程，沒有後續推進。
- 權限沿用 STORE_CUSTOMER_ORDERS；所有日期、進度與版本限制在 Worker 驗證，前端只作引導。

## 4. 訂購修改與理由

使用者要求：叫貨之前可自由修改；叫貨之後修改必須附理由，下拉＋其他輸入。

推薦補完：
- 新增預設「訂購」，此階段修改日期、聯絡資料、品項、數量、單價、訂金、備註不需理由，但仍寫歷程。
- **一旦曾經叫貨，之後即使退回訂購，修改仍要理由**，避免以退回繞過要求。以不可逆的 firstOrderedAt／hasEverOrdered 判定，不用目前狀態猜測。
- 修改理由選單建議：顧客變更需求、品項／數量調整、價格／訂金更正、聯絡資料更正、備註補充、輸入錯誤、其他。選「其他」必填說明；其他選項可補說明。這組為建議預設，待審核。
- 類別與補充文字分開儲存，不塞進業務備註；允許的值、非空及長度由 server 驗證。理由總顯示文字上限 300 字，與既有欄位限制協調。
- 未變更任何欄位不增加版本、不新增虛假修改紀錄；真正修改記欄位前後值及品項新增／刪除／變更。
- 已取貨及已取消維持原有不可修改保護；取貨誤按可先退回通知再附理由修改。取消恢復／取消訂購內容修正暫不開放。
- 既有黑名單電話檢查仍須 server 強制：拒絕訂購／需收全款不可被修改流程繞過。金額重算與訂金範圍沿用既有契約，不改成自動收款。

## 5. 取消理由與黑名單流程

取消入口位於操作欄；開啟共用取消視窗，顯示訂購識別與顧客，選理由：
1. 絕版／停產
2. 缺貨
3. 顧客取消
4. 其他（必填文字）

所有取消均要有效理由類別；預設不自動選中一個理由。前 3 項可填補充。欄位仍需避免超過 300 字。已結案不直接取消，先依誤操作更正退回；取消後保留資料與過往進度日期，未完成欄顯示 —，不再提供下一步按鈕。

### 5.1 儲存時詢問：只用「是／否」

- 絕版／停產、缺貨：直接取消，不因供應商因素新增黑名單事件。
- 顧客取消、其他：儲存時先以標準化電話查黑名單。若不在黑名單，詢問「是否加入黑名單？」；**按鈕文字只有「是」與「否」**。
- 「是」＝加入黑名單：保留取消草稿，開啟既有黑名單視窗，預填姓名、電話、原因及來源訂購；處置（拒絕訂購／收全款）可見且可修改。
- 「否」＝只取消訂購：提交取消與訂購操作紀錄，不建立黑名單或黑名單事件。
- 關閉詢問保留取消草稿，不當成選否或選是。
- 新黑名單視窗儲存時，將取消＋黑名單＋此次原因事件＋兩邊操作紀錄原子提交；之前顯示取消尚未儲存。關閉該視窗返回取消草稿，不送出半套變更。

### 5.2 電話已在黑名單（使用者補充）

- 顧客取消／其他情況查到同電話：直接顯示「已在黑名單，將新增本次事件紀錄」，不再問是否建立重複黑名單，也不重建主檔。既有其他原因取消仍不自動增加顧客不良事件。
- 儲存取消時，將**本次訂購造成的事件**追加到既有黑名單：來源訂購、日期、品項摘要、取消原因、補充、登記人與登記時間。訂購取消與事件同批提交。
- 既有處置、主檔姓名及原理由不自動覆寫；若要加重處置，由同事查看紀錄後在黑名單視窗手動修改。
- 第二次再有不同訂購事件就新增一筆；同一次取消的重送不能重複計次。同一訂購本階段無取消後恢復，不會重新取消計次。
- 主檔電話唯一；多人同時新增相同電話時不盲目 upsert，重新核對後決定新增主檔或追加事件，避免覆寫處置。

### 5.3 黑名單事件與手動調整處置

- **黑名單可以沒有事件紀錄**：直接手動新增黑名單，填姓名、電話、理由與處置即可，不強制補一筆訂購事件。一般系統新增／修改 Audit 仍保留，與此處「造成黑名單的事件」是兩回事。
- 從訂購轉入／追加黑名單必有事件，能看出「哪筆訂購、做了什麼、為何列黑名單」，不能只留下泛稱「顧客取消」。
- 黑名單清單建議顯示事件筆數與可展開入口；0 筆顯示「無訂購事件紀錄」，不是錯誤。多筆可按時間展開來源訂購與原因，僅有權者可看詳細內容。
- 事件累積作為人員判斷依據，**不自動加重處置**。例如原收全款、再發生一次取消，保留原處置，讓同事決定是否改為拒絕訂購；手動處置調整需留下前後值、理由、操作人與時間。
- 事件採 append-only，修正以補充／更正事件處理，不改掉原事件；移出黑名單不能連帶刪掉訂購操作歷史，歷史事件的保存與關聯需納入 migration／備份。

## 6. 每筆操作紀錄（平時收合）

每列操作欄有「展開紀錄」圖示，使用 aria-expanded／aria-controls；點擊後該訂購下一列展開 colSpan=14 的紀錄區，不跳頁，可再次收合。

- 內容：時間、操作人、事件、狀態前後、修改欄位前後、理由、關聯黑名單處置。類型包括建立、修改、叫貨、到貨、通知、取貨、退回、取消、加入黑名單／追加黑名單事件／手動處置調整，以及各步驟日期更正。
- 最新在前；長內容可換行，品項差異清楚列新增／刪除／數量與單價變動，不只寫「修改了一筆」。
- 預設不載完整歷程，展開才讀，分頁／載入更多（建議每次 20 筆）；主列表不對每筆做 N+1 查詢。成功更新該筆後失效其歷程快取。
- 每筆專屬歷程為 append-only 的業務明細，與既有 AuditService 的事件索引同批提交；不把帶電話、姓名、備註的完整差異散落到一般技術 log 或公開 repo fixture。
- 讀取、寫入均受既有模組權限限制；操作者從受權 session 取得，不採信前端傳入姓名。
- 舊資料沒有完整歷程時標示「舊版紀錄不完整」；可讀到可靠舊 Audit 才呈現摘要，不捏造過往欄位或日期。

## 7. 資料與 API 實作建議（待審核）

### 7.1 狀態相容與時間

保留既有 ORDERED 代表「叫貨」，新增 REGISTERED 代表「訂購」；新建單預設 REGISTERED。不能將舊 ORDERED 一律改為訂購，否則使用者原本的叫貨狀態會消失。

- 訂購表擴充各步驟作業日（ordered_date／arrived_date／notified_date／picked_up_date）、hasEverOrdered／首次叫貨的系統提交時間、取消類別／補充、必要的 legacy provenance；note 沿用。舊 notified_at 保留作原始歷史，不拿補登日期覆寫系統時間。日期欄允許 null 僅代表從未登記／舊版未知；已登記後任何 API 都不允許清空。
- 曾叫貨記號與首次系統提交時間不因退回或日期更正清除。舊 ORDERED／ARRIVED／NOTIFIED／PICKED_UP 保守視為曾叫貨（可用 migrated hasEverOrdered 記號，**不要造假的日期**）；舊 CANCELLED 原來源不確定，維持終止及未知標記。
- 舊 notified_at 若可信，轉成台北通知作業日並保留原值與 migration 來源；其餘歷程無法證實時顯示「未記錄」，不同於尚未到達的 —。禁止直接用 updated_at 猜所有步驟日期。
- 現 CHECK 不含 REGISTERED，需要 forward migration；不得改已發布 migration、清空資料或重建成無內容。若重建表，須完整保留 lines 外鍵、索引、資料與 metadata，驗證筆數與金額。
- 新建 order_events（名稱待實作定案）：order_id、事件序、actor、時間、事件類型、from/to、理由類別／補充、結構化欄位／品項差異、關聯黑名單 ID 等。由服務端產生，不提供直接編輯／刪除歷程 API。
- 新增 blacklist_events：blacklist_id／來源訂購 ID／事件類型／取消原因與摘要快照／操作者／系統時間，來源事件具去重鍵；既有及手動新增黑名單允許零事件。不得以沒有事件判為損壞資料。主檔需 version 保護人員手動調整處置，事件追加與主檔調整是不同動作。事件關聯與移出保存策略應避免 CASCADE 刪除歷史。

### 7.2 路由與交易

- 保留 `/orders` 清單／新增與 `/orders/:id` GET/PATCH；清單擴充日期、備註、曾叫貨、歷程是否可展開等必要欄位，不帶完整歷程。
- `/orders/:id/status` 可保留入口，但改成明確 action（advance／rollback／cancel）、前進時必填 milestoneDate 與 expectedVersion；Worker 依資料庫 current status 計算目標。若保留傳 target status，也必須 server 檢查相鄰狀態，不能舊客戶端跳階。
- 已登記日期的更正提供明確 milestone-date 操作（可獨立 PATCH endpoint），帶步驟代碼、非空作業日與 expectedVersion；不變更處理狀態，記日期前後值。拒絕未達步驟直接登記與非法清空。
- `GET /orders/:id/history?cursor=...&limit=20` 與黑名單事件查詢：受權、穩定排序、限制上限；主列表以批次聚合事件數量，不逐列讀全部事件。
- 修改／前進／退回／取消都以同一 order version guard 在 batch 中檢查、更新、加版本、寫歷程與 Audit；失敗整批回復。重複點擊、網路重送要有 request token／去重契約，不能重複進兩階或新增兩筆歷程。
- 選擇「取消＋黑名單」時同批驗證訂購與黑名單版本，建立主檔、追加原因事件與手動修改處置必須是明確不同操作；移除舊 API 可任意 upsert 的繞過路徑。
- 確認 schema 與 history table 全數登記到 portable backup 的列清單／欄位清單、還原依賴順序；舊備份缺新欄位需有明確相容處理，不能令還原後新資料丟失。
