## 1. 範圍與交付順序

| 階段 | 要交付 | 明確排除 |

### 商品主檔與費用的輸入界線（使用者本輪補充）

- 商品主檔的成本稅別直接改為「含稅／未稅（外加）／不計稅」三種，新增與修改必填、無預設；不是只在毛利頁加另一套稅別。待補只是舊資料缺漏狀態，不是第四個可選稅別。
- 成本、成本稅別、門市價、診所價、各批發單位售價與各平台網路售價全部來自商品主檔；分析頁不得新增任何可覆寫上述值的輸入，也不能把試算售價或試算成本另存一份。
- 第一階段分析頁全部唯讀。第二階段可新增／修改的是手續費、活動折扣、物流補貼及其他銷售費用規則；優惠折抵由規則計算，不回寫成另一份商品定價。
- 數量、訂單金額／其他商品金額、試算時間等第二階段情境條件只描述適用訂單，不能用來覆寫選定商品的單價、成本或稅別；比較新舊費用規則時也使用同一商品主檔版本。
- 若要變更成本或售價，回到既有商品主檔編輯與權限流程，儲存成功後再重讀毛利。Worker API 同樣不接受客戶端傳入替代成本／售價當計算權威。

## 3. 第一階段執行步驟

### P1-1：確定資料對應與合成驗收案例

1. 在上述基準逐一核對商品成本所屬基準單位、售價、批發單位、既有輸入／儲存／備份及所有稅別使用處。
2. 建立含稅、外加稅、不計稅、舊 none／NULL、缺成本、缺售價及不同單位的合成 fixture。
3. 產出 schema 變更方案與欄位對應表，寫入該階段 handoff；schema 編號由實作當時最新 migration 決定，不預占版本或編號。
4. 正式資料量盤點留待具體授權的發布準備，規劃及開發只讀 source、使用隔離 fixture。

完成條件：能從欄位追溯到唯一主檔，且不依商品名稱猜稅別、單位或成本。

### P1-2：成本稅別必填、遷移與備份相容

| 新選項 | 建議存碼（待 Claude 核對） | 原始成本 C 對應付款 | 毛利計算成本 |
| --- | --- | --- | --- |
| 含稅 | inclusive（沿用） | C | C ÷ 1.05 |
| 未稅（外加） | exclusive（沿用） | C × 1.05 | C |
| 不計稅 | no_tax（新增，與舊 none 區分） | C | C |

- 計算沿用使用者提供的前提：一般應稅交易、稅率 5%、進項符合扣抵條件；不新增公司層級扣抵設定。特殊或不可扣抵情況不冒用此結果，另案處理。
- 可扣抵進項稅額＝付款金額－毛利計算成本；「不計稅」為 0，僅代表此試算方式，不是免稅或免開發票的法規判定。
- 舊 inclusive／exclusive 保留原值；舊 none 與 NULL 顯示「待補資料」，不能直接轉成 no_tax。建議 forward migration 將 none 正規化為 NULL；若發現其他舊碼，先報告來源再決定對應，不猜測。
- DB 保留 NULL 容納尚未補正的既有商品；新建／修改 profile 的 Worker 驗證及表單要求三選一、紅色必填記號、無預設。既有商品仍可唯讀查看，修改儲存前必須補稅別；不得用 DB DEFAULT 隱性填值。
- 檢查停用／啟用等透過 profile update 的既有入口，待補商品需導向同一商品編輯補正，不另設繞過必填的寫入路徑。
- 新碼會超出舊 CHECK：以新的 forward migration 處理，保留 items 身分、參照、索引、trigger、revision、價格及單位資料；若需要重建表，須在隔離 D1 驗證整條 migration chain，不能以正式站手改取代。
- 舊備份的 none 同樣升級到待補狀態，新備份保留明確新碼；檢查 portable backup、migration marker、還原與 schema validator。
- 稅別補正沿用商品 revision／既有 mutation transaction，影響計算的成本及稅別更動透過共用 Audit Core 記錄前後值與操作者；不替純唯讀試算建立寫入紀錄。

完成條件：舊資料不被猜成不計稅；必填涵蓋前後端；價格／單位及相關資料保留；舊備份可還原成待補狀態。

### P1-3：建立唯一 Worker 毛利計算核心與唯讀查詢

1. 建議新增 `worker/item/item-margin-service.ts`（業務讀取與計算）、`shared/item-margin.ts`（回應型別），由既有 ItemRepository／ItemService 供應主檔；必要時在 Worker 內抽純計算函式供第二階段重用。
2. 新增建議路由 `GET /api/business/items/:id/margin`，沿用既有 CYID／ITEMS 授權；只有 DEFECTS 權限者不得取得成本／毛利。路由最終名稱以實作差異及 handoff 記錄。
3. 回傳商品 id／revision、基準單位、計算前提、成本摘要、門市一列、診所兩種解讀及各批發單位兩種解讀；回應不含網路通路試算。
4. 原始主檔保持 scaled4，運算使用整數／BigInt 有理數；含稅拆算不先四捨五入到 2 位再算毛利。建議金額顯示 2 位、百分比顯示 2 位，以最後顯示時四捨五入，明細保留來源值及公式；舍入策略須寫入實作契約及測試。
5. 不持久化衍生毛利，不在前端維護第二套公式；前端僅格式化 Worker 結果。HTTP 以十進位字串傳遞結果，BigInt 不直接 JSON 序列化。
6. 按單一商品 id／既有 item_id 索引讀主檔與換算／批發列，不做全商品重算、背景輪詢或網路平台逐列查詢。

計算定義：

- 基準單位淨成本＝依成本稅別換算的成本。
- 銷售單位成本＝基準單位淨成本 × unitFactorToBase 的精確換算倍率。
- 門市淨收入＝門市含稅價 ÷ 1.05。
- 診所／批發未稅解讀：淨收入＝主檔售價；含稅解讀：淨收入＝主檔售價 ÷ 1.05。
- 毛利額＝該銷售單位淨收入－同單位成本。
- 毛利率＝毛利額 ÷ 淨收入 × 100%；不是以含稅收款或成本作分母。

資料狀態：

| 情況 | 結果 |
| --- | --- |
| 缺成本或成本稅別待補 | 成本摘要標示缺項；不產生依賴該資料的毛利 |
| 某通路缺售價 | 只標該列「未設定售價」，其他完整列照算 |
| 批發單位無換算路徑／循環／倍率無效 | 只標該單位「待補單位換算」，不得假設倍率 1 |
| 成本為 0 | 當成明確的零成本，可正常試算 |
| 售價為 0 | 毛利額可為負成本；毛利率顯示「—／售價為 0」，不用 Infinity 或 0% 冒充 |
| 售價低於成本 | 保留負毛利與共用危險色提示 |
| 商品主檔修改成功 | 以新 revision 重新讀取試算；切商品或舊請求晚回時不可覆蓋新商品結果 |

完成條件：單一後端公式、精確單位換算、每列有完整或缺資料狀態；正式資料零寫入的唯讀試算。

### P1-4：接入商品詳情與共用介面

1. 保留「商品／瑕疵」頂層入口，在選定商品的詳情內增加「商品資料｜毛利分析」，不新增側欄主模組。
2. 成本摘要用 RecordSheet：原始進價、稅別、基準單位、進貨付款金額、可扣抵進項稅額、毛利計算成本分開列示。
3. 通路比較用既有 `cy-op-table cy-rt`：通路、單位、主檔售價、未稅解讀毛利額／率、含稅解讀毛利額／率；門市未稅解讀欄為「—」。每一批發單位各一列。
4. 毛利頁僅提供回到商品資料補正的入口，不複製成本或售價編輯表單。
5. 頁籤切換共用既有未儲存保護；只分析已儲存主檔，不能默默丟失草稿或把草稿值當已儲存成本。
6. 共用 Loading、FeedbackBanner、StatusChip、Dialog；手機沿用 820px、ModuleSections 及 cy-rt／data-label，缺共用呈現才擴充 src/ui/mobile，不新增另一套手機 state／計算。

完成條件：桌機及手機同資料、同計算與同權限，明細子頁不破壞既有商品與瑕疵導覽。

## 4. 第二階段執行步驟（全部網路價範圍）

### P2-1：定義訂單試算條件、費率與活動版本

- 沿用 item_web_platforms／item_online_prices 的平台 id 與商品售價，費率以平台共用管理，支援賣家資格／類別／商品／活動覆寫的明確優先順序，不能假設每平台只有一個費率。
- 新增費率、活動、疊加／分攤條件與提案版本；設計資料表時先比對現有設定／BOT／Audit，避免新增同職責主資料。
- 費率含固定／百分比、基礎、上下限、稅別及扣抵條件、範圍、生效期間、官方來源、查證日期、審查狀態及版本。
- 活動含固定券、折扣券及折抵上限、滿額／滿件、平台／賣家負擔、物流補貼、互斥／可併用、適用範圍與日期；固定費有明確訂單分攤方式。
- 定義台北時區生效／失效邊界、試算時間、一般情境的商品數量／訂單總額／其他商品金額、可用券、賣家方案及分攤方式。
- 先寫規則／前後版本、權限表與驗收 fixture，不能用不完整規則生成宣稱完整的毛利區間。

完成條件：每個情境可重現，日期、計費基礎、優惠歸屬、疊加與分攤均可判定；生效後修改建立新版本，歷史試算能引用當時版本。

### P2-2：擴充同一核心，計算網路基本毛利與貢獻利率

- 網路定價一律含稅；基本毛利沿用第一階段公式。
- 在指定訂單條件與有效規則集合內列舉合法組合，依實際收費順序、上限及取整處理；互斥活動不可同扣，不將所有優惠直接相加。
- 每個合法組合拆開買家支付、賣家折讓、平台補貼及賣家實際費用，避免平台補貼誤當賣家損失或同一折扣扣兩次。
- 以情境下賣家實際未稅銷售收入作分母；賣家折讓先反映收入，貢獻額再扣商品成本與可歸屬費用。平台補貼的收入／稅務歸屬依查證規則表示，不盲目增加或扣除。
- 最差／最佳按貢獻利率排序，同時回傳金額，不能只用「費用最高／最低」代替利率極值；一般情境依使用者指定條件計算，不假裝統計上的常見值。
- 區間清楚標示適用訂單條件、時間與規則版本；缺規則顯示待確認或「已知規則範圍」，不是所有訂單的保證上下界。
- 回傳逐項公式、折扣分攤、費用基礎與稅務換算、收入／成本／貢獻額／率、規則來源。
- 採按需試算，估算有效組合數與讀寫量；必要時有界分批／可續跑並揭露未算完，不能截斷後仍宣稱得到完整極值。

完成條件：平台／賣家負擔正確、折扣不重扣、合法情境與分母清楚；相同來源與版本得到相同結果。

### P2-3：平台分析、優惠與費率管理介面

- 在既有毛利分析詳情加入平台比較與展開明細：基本毛利、費用後貢獻額／率、最差～最佳、一般情境、完整度與來源。
- 管理區明示設定作用於全平台、類別或指定商品，避免在單品頁誤以為只改該商品。
- 新增／修改沿用 RecordRows、Dialog＋EntryTable；審核、歷史、停用、生效狀態使用既有權限、確認與 Audit。
- 費率提案先顯示新舊規則及影響比較，由有權限的人核准後才生效；不以建立提案或 AI 查證代替核准。

### P2-4：受控 AI API、核准與通知

| 能力 | 套用界線 |
| --- | --- |
| 查商品／設定／版本、試算／影響比較 | 最小範圍唯讀；沿用 CYID／Worker 既有授權模式 |
| 建立優惠草稿 | 結構化、檢查重複與衝突，資料不完整時回待補 |
| 套用優惠 | 使用者明確授權、內容完整及有寫入權限後才套用，帶 expectedRevision／重複請求識別 |
| 提交費率提案 | 必須官方來源、生效條件與新舊影響，僅建立待審版本 |
| 核准費率 | 人工審核權限；AI 提案身分不可呼叫核准路徑或自動啟用 |
| 查審核／歷史 | 保留來源、操作者、前後內容、版本及生效時間 |

- 先提供受控 REST contract 與工具 schema，需要時再包 MCP，不另造授權 authority、不給 AI D1 憑證。
- 有寫入的操作沿用 revision 衝突 409、原子 transaction、共用 Audit Core；重複套用不能新增重複活動。
- 變更後以同一 Worker 計算核心重新試算，避免 AI 自訂公式。
- 既有 BOT 中心只串接適合的待審／結果通知，不把機器提案或優惠管理強塞進社群發文審稿；核准 authority 留在費率 service。
- API 身分方式與角色範圍須在該階段 handoff 寫明，不能把 browser session 或現有小編 token 任意擴權。
